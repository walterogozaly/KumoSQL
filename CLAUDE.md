# Repository instructions for Claude

SQLGlot standard: `sqlglot==30.21.0` is the only supported version. Walter fully approved this transition ([#716](https://github.com/walterogozaly/KumoSQL/issues/716)). Routine CI and Dell full-suite runs use the matching compiled `sqlglotc==30.21.0` build once per revision. Do not restore the 26.0.0 / 30.20.0 compatibility matrix or a second routine full-suite pure-Python run. Pure Python remains usable; use `--pure` for focused diagnostics when needed. Future version changes require explicit validation and an intentional update to the pin, CI and docs.

Keep documentation and README files up to date when your changes affect setup, usage, behavior, or developer workflows. Include those updates in the same pull request.

The README is the overview: the scoreboard, a short summary per feature, the CLI table and the laptop-replica smoke test. Feature details live in `docs/` (for example `docs/ui.md`, `docs/provers.md`, `docs/pipeline-analysis.md`, `docs/rewrite-rules.md`, `docs/cost-and-change-reports.md`, `docs/dataform-repositories.md`) and one page per eval in `docs/evals/`. `docs/README.md` indexes every page and `docs/evals/README.md` indexes the eval pages and names each eval's results file; list a new page in the matching index (`tests/test_docs.py` checks both indexes, that every results file is named, and every relative link). Put new detail in the matching docs page, and change the README summary only when the one-line description changes. When a README merge conflicts over a section that moved to `docs/`, apply your change to the docs page.

Every Markdown page in `docs/` has a plain-language companion at the same relative path in `docs_simple/`. Update both when behavior or usage changes, and list new companions in the simple index. Explain the purpose, a concrete example, and the limits of the evidence; link back to the full reference for API details and recorded scores instead of duplicating changing numbers. `tests/test_docs.py` checks companion coverage, both sets of indexes, reference links, and relative links.

Run tests with `python tools/run_tests.py` (parallel; `--evals` runs only the benchmark floors, `--no-evals` the rest; add `--label "<task>"` and `--target <test file>` for the tests your change is aimed at, so the test history can tell your failures from collateral ones, see `docs/test-history.md`). Tests must be safe to run in parallel: no shared files or module-level state between tests. When your work is complete, run the relevant tests and open a pull request. For code changes, run targeted regressions and affected evals first, plus `--routine` before queueing; shared prover, parser, normalization or execution changes require broader eval comparisons. Walter fully approved intermittent broad testing on October 5, 2026: use targeted regressions, affected evals and `--routine` for each exact candidate; run the full default suite including eval floors nightly and before releases. Shared prover changes still require broader base/candidate case comparisons and soundness guards before merging. This supersedes the earlier full-every-batch policy. Record exact SHA and coverage; never describe a routine result as full coverage. Documentation-only PRs may use the documentation checks without a full eval run. Enable auto-merge using the repository's usual merge method only when the applicable validation is recorded; absent branch protection does not waive this procedure. See [the merge testing procedure](docs/test-history.md#merge-testing-procedure). If auto-merge cannot be enabled or a conflict blocks merging, report the blocker and leave the pull request open.

Benchmark scoreboard: the README's scoreboard is generated from `benchmarks/results/*.json`, one file per eval. Any change that moves an eval's score, or adds an eval, must update that eval's results file (score, size, date, caveats; keep "0 wrong" honest) and run `python tools/scoreboard.py` in the same pull request. Never edit the README table by hand. If the table conflicts when merging, keep either side and rerun the script. Mention the same numbers in the eval's own docs page under `docs/evals/`.

A change meant to leave every score alone (a refactor, a shared helper, a cleanup) should show it: `python tools/eval_diff.py` reruns every eval on `origin/master` and on your checkout and reports any eval whose answers differ.
