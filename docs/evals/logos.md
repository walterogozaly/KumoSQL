# Logos' TPC-H, DSB and TPC-DS rewrite pairs

[Logos](https://github.com/WindOctober/Logos/blob/main/benchmarks/core/README.md) (MIT) keeps a corpus of SQL rewrite pairs with their provenance under `benchmarks/core`. Three of its folders hold pairs that no other KumoSQL eval scores, and `tools/logos_bench.py` scores those 73 pairs:

| Family | Pairs | What a pair is |
| --- | ---: | --- |
| `rbot-tpch` | 22 | An R-Bot TPC-H workload query (`queryN_0.sql`) and the SQL that R-Bot's pinned Calcite engine prints after applying one rule to it (`queryN_1.sql`). `rbot/rewrite-pairs.manifest.json` names the rule |
| `rbot-dsb` | 37 | The same for R-Bot's DSB workload |
| `tpcds-variants` | 14 | A TPC-DS query and the same query generated from the kit's variant template (`query_variants/queryNa.tpl`), which the TPC-DS specification offers as an alternative formulation |

A Calcite rule's output is a golden rewrite, not a proven label. Logos does not claim the pairs are equivalent, and neither does this eval: a pair that a database shows different is a **label failure**. It is kept as a negative that must never be proved.

The R-Bot rules are `AGGREGATE_PROJECT_MERGE` (27 pairs), `AGGREGATE_REDUCE_FUNCTIONS` (23), `FILTER_SUB_QUERY_TO_CORRELATE` (4), `AGGREGATE_EXPAND_DISTINCT_AGGREGATES` (2), `FILTER_INTO_JOIN` (2) and `AGGREGATE_CASE_TO_FILTER` (1).

## Source, licence and pin

The pairs come from Logos commit `333d5275ac871f5b36ce3a7dc5f6fef5f7879069`. Logos' own code is MIT. The R-Bot workload is Apache-2.0 (`licenses/RBot-LICENSE`), and the TPC-DS kit's text is under the TPC end-user licence (`licenses/TPCDS-EULA.txt`). The TPC-derived query text is therefore fetched at run time and never committed, like the other TPC harnesses here. `python tools/benchmark_corpora.py fetch logos` makes a sparse clone of `LICENSE`, `benchmarks/core/licenses`, `rbot` and `tpcds` at the pin into `$KUMOSQL_BENCH_DIR` (default `~/.cache/kumosql-bench`). `tests/fixtures/logos/pairs.json` holds only the SHA-256 of every file used (checked before every run), each pair's rule, and this eval's own labels: `label_failures`, with the reason for each, and `known_wrong`, which is empty.

The data is generated by the existing fetchers: TPC-H at scale 0.1 with `tpchgen-cli`, and TPC-DS at scale 1 (the smallest `dsdgen` allows) with DSB's `dsdgen`, whose value distributions differ from the official kit's. `fetch_tpcds_data` now passes `dsdgen` a relative `-DIR`, because a long absolute path overflows its fixed buffer.

## How a pair is scored

Each pair goes through two checks that do not trust each other.

1. **Proof.** `prove_equivalent_algebraic` runs on the pair converted from PostgreSQL to BigQuery, then on the pair converted to MySQL (the route `tools/rbot_bench.py` takes for R-Bot's Calcite pairs). Output names are ignored, arithmetic is exact, and the NOT NULL columns and primary keys of the workload's `create_tables.sql` are used. R-Bot's TPC-H schema declares no keys, so those proofs hold over every database that has its NOT NULL columns. Calcite names a derived table's columns in its alias (`AS t (a, b)`), which neither BigQuery nor MySQL can express. KumoSQL's `expand_alias_columns` therefore moves the names into the derived table before conversion. Each route has a 120-second wall-clock limit.
2. **Data.** Both queries run in DuckDB:
   - on the generated TPC-H or TPC-DS database;
   - on small databases built for the pair from the declared schema by `kumosql.counterexample.find_counterexample`: 150 random databases, then the targeted suite.

   A difference counts only when DuckDB returns the same rows with its optimizer off (`kumosql.duckdb_load.run_unoptimized`). A difference on a small database must also survive row shuffles. Under a root `LIMIT`, the rows must differ with the `LIMIT` removed too, so a different pick among ties is not a difference. If the unoptimized run cannot finish on the generated data, the difference is reported as `unconfirmed` and counted nowhere.

Outcomes:

| Outcome | Meaning |
| --- | --- |
| `proven` | Proved, and no database separates the two queries |
| `refuted` | Not proved, and a database separates the queries (a label failure) |
| `unknown` | Neither |
| `unsupported` | Neither route can read the pair |
| `timeout` | A route reached its time limit |
| `error` | A crash |
| `wrong` | Proved, yet a database separates the queries; must stay 0 |

A file with two statements is handled as follows. For R-Bot, Logos' rule applies and the first statement is used (DSB `query039`). TPC-DS `query014` has two statements on each side, and both statement pairs must be proved.

**Adapted cases.** The TPC-DS kit's `ansi` profile prints `SELECT TOP n`, always on the outermost select, and `date + 14 days`. These are read as `LIMIT n` and `date + INTERVAL '14' DAY`. All 14 TPC-DS variant pairs need the `TOP` change and are counted as adapted. The R-Bot pairs are used as written. On the generated TPC-DS data, `customer.c_last_review_date_sk` (Logos' DDL) is named `c_last_review_date` (DSB's DDL), and the harness maps it.

**Held out.** One case in five is held out, chosen by the SHA-1 of its id (`benchmark_corpora.held_out`). That gives 12 of the 73 cases.

```bash
python tools/benchmark_corpora.py fetch logos tpch-data tpcds-data
python tools/logos_bench.py --jobs 4                    # every pair (about 25 minutes on 3 busy cores)
python tools/logos_bench.py --split dev --show          # the pairs used while developing, with each check
python tools/logos_bench.py --family rbot-tpch --show   # one family
python tools/logos_bench.py --write-results             # also write the two results files
python tools/logos_bench.py overlap                     # the VeriEQL and WeTune overlap, by text
```

Without the generated databases, the data check falls back to the small databases alone. `tests/test_logos_bench.py` covers the following:

- the pins and the TPC-DS adaptations;
- the outcome rules;
- the 22 R-Bot TPC-H pairs: no wrong proof, and at least 15 proved;
- every recorded label failure stays unproved.

## Scores

Measured on 2026-10-03 on master `a481075` with this harness. No prover change was made for this eval.

| Results file | Score | Held out |
| --- | --- | --- |
| `logos-core-proof` | **36/69 proved, 0 wrong** (4 label failures set aside; 7 unknown, 22 unsupported, 4 timeouts) | 5/11 proved, 1 refuted, 0 wrong |
| `logos-core-executed` | **4/73 shown different, 0 wrong** (3 on a small database, 1 on the generated data) | 1/12 |

By family:

| Family | Proved | Refuted | Unknown | Unsupported | Timeout |
| --- | ---: | ---: | ---: | ---: | ---: |
| `rbot-tpch` (22) | 16/21 | 1 | 1 | 4 | 0 |
| `rbot-dsb` (37) | 18/36 | 1 | 6 | 8 | 4 |
| `tpcds-variants` (14, all adapted) | 2/12 | 2 | 0 | 10 | 0 |

Every proof's two queries also return the same rows on the generated data and on every small database. The **baseline**, before either harness fix, was 23/69 proved, 4 refuted and 0 wrong (5/11 held out). Both fixes were developed on the dev split, but the baseline listing showed the failure reason of every pair, held-out ones included. That exposure is recorded as "tuned on test" in the results files; the held-out score did not move. The timeouts depend on load: the 120-second limit is wall-clock time, and the measurement ran on a busy shared machine.

Most `unsupported` pairs fail on one of these:

- a query that one of KumoSQL's normalisations cannot print back faithfully in the target dialect (most TPC-DS variants, which use `ROLLUP`, `GROUPING` and `||`);
- `NULLS FIRST`/`NULLS LAST` that MySQL cannot spell;
- `LIMIT` on a scalar aggregate with no `ORDER BY` (TPC-H Q14, Q17, Q19);
- a `UNION` inside a predicate subquery (TPC-DS Q35).

### Label failures

| Pair | Rule | Where | Why the two queries differ |
| --- | --- | --- | --- |
| `rbot-tpch/query1` | `AGGREGATE_REDUCE_FUNCTIONS` | TPC-H data | `AVG(x)` becomes `CAST(SUM(x) / COUNT(*) AS DECIMAL(15, 2))`, which rounds to 2 places, because Calcite types `AVG` of a `DECIMAL(15, 2)` column as `DECIMAL(15, 2)`. `avg_qty` is 25.537587 against 25.54 |
| `rbot-dsb/query080` | `AGGREGATE_REDUCE_FUNCTIONS` | small database | The outer `SUM("returns")` under `GROUP BY ROLLUP` becomes `COALESCE(SUM("returns"), 0)`. The grand-total row over no input rows is then `0.00` instead of `NULL` |
| `tpcds-variants/query014` | variant 14a | small database | The manual `ROLLUP` expansion returns a grand-total row of NULLs where the base query returns rows, and its second statement returns nothing where the base returns a row. The generated data agrees |
| `tpcds-variants/query036` | variant 36a | small database | `ROLLUP` written as a `UNION` of groupings returns one row of NULLs where the base query returns three. On the generated data the optimized runs differ too, but the unoptimized run did not finish |

The TPC-DS variants are equivalent on TPC-DS-shaped data. The small databases respect only the declared keys and NOT NULL columns, not the kit's foreign keys or its never-empty fact tables, so these two failures show that the pairs are not equivalent over every database with that schema.

## Overlap with other evals

Checked by text with `python tools/logos_bench.py overlap`. Whitespace, quotes and case are ignored.

| Logos folder | Pairs | Covered by | Same text |
| --- | ---: | --- | --- |
| `verieql/calcite` | 236 | [VeriEQL Calcite](verieql.md) (397) | 236/236 |
| `verieql/literature` | 30 | [VeriEQL Literature](verieql.md) (64) | 22/30 |
| `wetune/issues` | 50 | [WeTune issues](rewrite-benchmarks.md#wetunes-50-github-performance-issues) (WeTune-code `f99ee9e`) | 50/50 |

The 8 literature pairs that differ are Logos' rewordings of VeriEQL pairs 4, 7, 13, 28, 30, 32, 48 and 49:

- `EXISTS` written as `IN`;
- a bare `(R UNION ALL S)` spelled as selects, which KumoSQL's VeriEQL harness also does;
- a comma join with `ON` written as `JOIN`;
- one `HAVING` moved into a derived table.

They add no new source pair, so these two folders are not scored again.

The 73 scored pairs overlap no existing eval:

- **R-Bot's Calcite pairs** (`rbot-calcite`, 45 pairs on Calcite's test schema): none of them.
- **SQLSolver's TPC-H pairs** (`sqlsolver-tpch`): none, even with constants ignored.
- **Same templates, different instances.** The R-Bot TPC-H sources are TPC-H's 22 queries, and 5 match the transformation bench's TPC-H queries once constants are ignored. 33 of the 37 R-Bot DSB sources match one of the DSB template instances in [analytical coverage](analytical-sql-coverage.md) once constants are ignored, and none matches as text. 13 of the 14 TPC-DS variant base queries match a TPC-DS stream-0 query of the [transformation bench](transformation-bench.md) once constants are ignored.
- **Rewrite targets.** No Calcite output or TPC-DS variant appears in any other corpus. Those benches transform single queries; none of them scores these pairs.
