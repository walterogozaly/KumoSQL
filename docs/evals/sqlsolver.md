# Algebraic prover (SQLSolver's arithmetic) for BigQuery and Dataform SQL

[Plain-language version](../../docs_simple/evals/sqlsolver.md)

KumoSQL ports the core of [SQLSolver](https://github.com/SJTU-IPADS/SQLSolver) (SIGMOD 2024, Apache-2.0) to Python on top of `z3-solver`. What is taken is its *system of arithmetic*: a query is a function from tuples to multiplicities (natural numbers), so under bag semantics `UNION ALL` is addition, a join is multiplication, a filter or projection is linear, and equivalence becomes an arithmetic identity that an SMT solver can decide. Everything runs in pure Python from a user-level `pip install`, so it works on locked-down work computers: no Java, no native Z3 build, no admin rights.

## Plan

1. **Algebraic normal form (done, `algebraic_equivalence.py`).** Joins, filters and projections distribute over `UNION ALL`; `COUNT`, `SUM`, `MIN` and `MAX` over a union become partial aggregates combined arithmetically (with or without `GROUP BY`); redundant regrouping is dropped; union shapes are canonical. Every rewrite is checked against SQLite on random databases (NULLs and empty tables included).
2. **Multiplicity algebra (next).** Replace text-matching of derived tables with a real intermediate representation: queries as sums of products of table multiplicities, `DISTINCT` as squash (`‖x‖`), selection as an indicator, and unification of bound tuple variables. Equivalence of two normal forms is discharged by Z3 over integers. This subsumes the bijection search in `smt_equivalence.py` for bag queries and handles nested derived tables and CTEs uniformly.
3. **LIA\* reduction.** SQLSolver's key step for aggregates over joins and nested subqueries: group cardinalities and per-group sums are encoded as sets of integer vectors with a star operator, then reduced to plain linear integer arithmetic (a Parikh-style closed form) that Z3 decides. Done in Python with `z3-solver`; the reduction is validated against SQLSolver's published benchmarks (Calcite, TPC-H) and the existing SQLite fuzz harness.
4. **BigQuery and Dataform front end.** Schemas come from Dataform declarations and BigQuery table metadata (types, `NOT NULL`, partition and unique keys when known, which strengthen proofs). Dialect handling for `SAFE_*`, `IFNULL`, date functions and `UNNEST` stays conservative: unsupported shapes return `not_proven`, never a wrong proof.
5. **Pipeline and UI.** Rewrite verification and the equivalent-work reports use the algebraic prover; a Settings toggle and a status line show which stage produced each proof.
6. **Optional Java SQLSolver (kept as a cross-check, done as an adapter).** `sqlsolver_backend.py` can run the real jar from a user folder when present, as a second opinion after the Python prover. It is never required. A setup helper and Windows validation of this path are last and lowest priority.

## Windows without admin rights

Steps 1–5 need only `pip install --user` (or a venv) for `sqlglot` and `z3-solver`; the z3 wheel bundles its own native library. Only step 6 needs Java, a Z3 Java binding and Windows Z3 DLLs, all fetched into one user folder (`KUMOSQL_SQLSOLVER_HOME`, default `%LOCALAPPDATA%\kumosql\sqlsolver`). SQLSolver's license (Apache-2.0) permits redistribution with its LICENSE and NOTICE; nothing is vendored today.

## Optional Java backend

`prove_equivalent(left, right, schema=...)` in `sqlsolver_backend.py` runs the algebraic prover first and asks the real SQLSolver only when no proof is found. Layout of the user folder:

```
<home>/sqlsolver.jar     built with `gradle fatjar` from SQLSolver (Java 17)
<home>/lib/              Z3 4.13 natives: libz3 + libz3java (.dll / .so / .dylib)
<home>/jre/bin/java      optional portable JRE 17+, used when no Java is on PATH
```

Java is taken from `KUMOSQL_JAVA`, `<home>/jre`, `JAVA_HOME`, then `PATH`; `python -m kumosql prove-sql-sqlsolver --check` says what is missing. BigQuery SQL is parsed with sqlglot and re-emitted as one line of Calcite SQL (table names flattened to one identifier, schema as `CREATE TABLE`). Queries using `UNNEST`, `QUALIFY`, windows, arrays, structs, `PIVOT`, `TABLESAMPLE`, nondeterministic functions or tables missing from the schema are refused. SQLSolver answers `EQ` when both queries fail its semantic checks, so each query is also compared with an always-empty wrapper of itself; a control that comes back `EQ` voids the proof. SQLSolver's `NEQ` carries no counterexample, so it is reported as `not_proven`; counterexamples come from the Z3 stage.

## Benchmark coverage

`tools/sqlsolver_bench.py` runs the benchmark pairs published with SQLSolver (copied to `tests/fixtures/sqlsolver/`, Apache-2.0, LICENSE alongside) through the prover. SQLSolver's authors state every pair is equivalent, so the benchmark measures how many pairs KumoSQL **proves** versus leaves **unknown**; a pair is never reported "not equivalent" just because it was not proved. Each proof is re-checked on 60 random DuckDB databases (NULLs, duplicates, empty tables; NOT NULL and primary keys respected), then on 60 skewed ones whose numbers come from a few values next to the queries' literals, shared by every table so join keys meet and rows repeat; any disagreement counts as a **wrong** proof. Small random databases repeat (empty tables, one-row tables), so a database the search already ran is not run again, and a table already holding the next database's rows is not reloaded; the answers are the same, with less DuckDB work (QED, Cosette and the other harnesses that call `sqlsolver_bench.differ` share this). `tests/test_sqlsolver_benchmarks.py` fails on any wrong proof or when a suite falls below its floor.

## Negated tests in every dialect

`x IS NOT NULL`, `x NOT LIKE y` and `x NOT ILIKE y` are rewritten to `NOT (...)` before either prover reads a query (`ast_utils.canonical_negation`). sqlglot parses them under PostgreSQL as the positive node with a `negate` flag, which an earlier version of the provers ignored: read as PostgreSQL, `x IS NULL` and `x IS NOT NULL` were proven equivalent. The BigQuery default was never affected. `tests/test_negated_predicates.py` pins it for five dialects.

## Rewrite verification and declared facts

`kumosql.prover_context.prove` is the one entry point the app uses; `verify_rewrite` calls it for any changed statement when the solver is enabled (`prover` section of the saved settings, default on, 5000 ms). The facts it may assume come from `kumosql.prover_schema`: BigQuery `REQUIRED` columns and `tableConstraints.primaryKey` from the saved catalog (`bigquery_catalog.saved_tables`), and Dataform `assertions` read by `pipeline_loading` into `Model.non_null` / `Model.unique_keys`. A table is registered under each spelling (`project.dataset.table`, `dataset.table`, `table`); a bare name shared by two tables is dropped. Proofs that used any declared fact list the assumption "declared keys and NOT NULL columns hold in the data".

## Saved equivalences and pipeline comparison

`kumosql.equivalences` stores declarations (`left`, `right`, `columns` pairs, `whole`) in `equivalences.json` in the data folder, one per `right` table and never cyclic. A declaration is an assumption on base relations: each reference to `right` is rewritten to `(SELECT left.x AS y, ... FROM left)`, so the solver sees one relation and keys, joins and aggregates reason over it unchanged. A columns-only declaration provides only the listed columns, so a query that reads another column of `right` fails to compile and stays unknown. Proofs that used a declaration list it in their assumptions.

`kumosql.pipeline_equivalence.prove_models` compares two models of a pipeline. Models are visited from the sources up; each model's SQL is read with equivalent tables substituted (declarations and earlier lemmas), compared only with models that now read the same tables, and a proved pair becomes a lemma (a positional column mapping) for the layers above. If the final models still differ, both are inlined as derived tables (400,000 characters at most) and the flat queries are compared. At most 300 solver calls are spent on lemmas; the result is `equivalent` only when every step was proven, with the lemmas and declarations used reported.

Everyday BigQuery refactors (CTE inlining, `USING` joins, `* EXCEPT`, `COUNTIF`, `SAFE_DIVIDE`, `QUALIFY` dedupes, `IN` versus `EXISTS`, windows through a CTE) are pinned in `tests/test_bigquery_refactors.py`, with near misses (a moved boundary, `SAFE_DIVIDE` versus plain division, a window ordered the other way) that must stay unproved.


## Keyed dimension joined to a grouped fact

With a declared key on `customers`, `customers JOIN (SELECT customer_id, SUM(x) ... GROUP BY customer_id)` is rewritten to the flat join grouped by the key, so a CTE-reuse refactor and its flat form are proved equal. Without the declared key nothing changes.

## Everyday refactors

`tests/test_bigquery_refactors.py` lists everyday BigQuery refactors the prover proves and near misses it refuses. Added in this round: a correlated scalar aggregate in the select list versus a left join to the grouped table (the inner join is refused), the sum of grouped sums versus the plain sum (a sum of grouped counts is refused: it reads NULL for no rows), `IN` over a `UNION ALL` versus an `OR` of the branches, a NULL guard under a global aggregate (refused under a `GROUP BY`), `LOWER(TRIM(x))` versus `TRIM(LOWER(x))` and `||` versus `CONCAT`, and a `LIMIT` inside a derived table that the outer select only projects versus the same `ORDER BY .. LIMIT` at the top.

`GROUP BY` or `DISTINCT` over a derived `UNION ALL` that only groups its own columns is rewritten to a set union,.

A `LEFT JOIN` to a derived table that only feeds `ind IS NOT NULL` (the shape decorrelators emit for `IN` and `EXISTS` under `OR`) is read as the `EXISTS` it stands for, when the join matches at most one row: the equated columns cover a declared key of the single table behind the derived table, or every column of its `GROUP BY`. Joined on a non-key column it stays a join, since the repeated rows would change the result.

A `FULL JOIN` filtered on one side by a comparison (`b.x > 1`) is the `LEFT` or `RIGHT` join that keeps that side, and on both sides an inner join. A `LEFT JOIN` whose derived table or keyed table is never read and matches at most one row is dropped. `VALUES` without column names has columns `expr$0`, `expr$1`, .. (Calcite's names). Nested set operations are re-parenthesized in the normalized text so it reads back with the same shape.

A `LEFT JOIN` whose far side a `WHERE` condition rejects when NULL (a comparison, `BETWEEN`, `IN (list)`, `LIKE` or `IS NOT NULL` on one of its columns, possibly through arithmetic, `CAST`, `UPPER` or `LOWER`; an `OR` counts only when every branch rejects it) is an inner join, since the condition drops exactly the null-extended rows. The same holds for a `LEFT JOIN` inside a derived table that only joins, filters and projects, when the outer `WHERE` rejects an output computed from the far side; `IS NULL`, `<=>`, `COALESCE` and `NOT IN` never count, and a chain with a `RIGHT`, `FULL`, `NATURAL` or `USING` join is left alone (`null_rejecting_joins.py`). A `WHERE` over a derived `UNION`, `INTERSECT` or `EXCEPT` whose branches only join, filter and project moves into every branch, rewritten by position with that branch's expressions, and a select that is left listing each output once (in any order, with an `ORDER BY` on those outputs) is the set operation itself (`union_filter_rules.py`).

A filter on the values a derived `DISTINCT` or `GROUP BY` keeps (its outputs, or its grouping keys) moves inside it; a select that lists every output of a derived `DISTINCT` is that derived select; and the deduplication of such a derived table is dropped under aggregates that ignore repeats (`MIN`, `MAX`, `COUNT(DISTINCT ..)`). `EXCEPT` of two filters over the same table, both listing every column, is one `DISTINCT` select with `AND NOT COALESCE(b, FALSE)`. `(SELECT 1 .. LIMIT 1) IS NOT NULL` is `EXISTS`, and `NTH_VALUE(x, 1)` is `FIRST_VALUE(x)`. A derived table's unnamed column gets a generated name so `SELECT *` can list it. `LATERAL`: a global-aggregate subquery (it always returns one row) is read as the scalar subquery it is, and an `INNER JOIN LATERAL` over a filter-and-project subquery as a join whose `ON` is the correlated part of its `WHERE`; anything else (a `GROUP BY`, `LIMIT`, outer-reference in the select list) is not proven.

A select that only keeps distinct values (`DISTINCT`, or `GROUP BY` with no aggregate) over a join reads each table as its distinct projection onto the columns the select uses, unless a declared key is among them; conditions on that table alone move inside. A select whose rows are provably all different (every table occurrence is pinned to one row through a declared key, or is a derived `DISTINCT`) is as good as a `DISTINCT` one, so it can match a `GROUP BY` form. In the select list, `x IN (SELECT y ..)` (also a tuple of columns) is `EXISTS` when every column on both sides is declared NOT NULL (otherwise `IN` can be UNKNOWN and is left alone), `CASE WHEN EXISTS (..) THEN TRUE ELSE FALSE END` is the `EXISTS`, and a left join to a constant `DISTINCT` select on `ON TRUE` is an `EXISTS` flag. `EXISTS` is a Boolean value in the select list.

`GROUP BY GROUPING SETS` is the `UNION ALL` of one grouped select per set: a key missing from a set reads as NULL, `GROUPING(a, b)` is the bit mask of the arguments missing from the set (the first is the high bit), and the empty set is a global aggregate. Integer comparisons and `CASE WHEN TRUE/FALSE` on literals are evaluated; a constant output of a derived select is read as that constant by the select over it, and a source that is one row of constants (`FROM (SELECT 5 AS x) AS c`) is dropped. `COUNT(NULL)` is 0 next to another aggregate or a `GROUP BY` (alone it is the one row of a global aggregate, so it stays). `INTERSECT` with an always-empty side, or `EXCEPT` of one, is empty.

A `GROUP BY` of exactly the selected columns inside an `IN` or `EXISTS` test is dropped (the test does not see repeats). `(x IS NULL) IS NULL` is FALSE and `(x IS NULL) IS NOT NULL` is TRUE (a null test is never NULL), `TRUE OR y` and `FALSE AND y` are decided, and `CAST(x IS NULL AS INTEGER)` (0 or 1) compared with a number outside `{0, 1}` is decided. A typed `CAST(NULL AS t)` is NULL. A `LEFT`/`RIGHT JOIN` whose null-extended side is always empty (`WHERE FALSE`) keeps the other side with NULL for the empty side's columns. An aggregate in the select list of an `IN` or `EXISTS` subquery is refused: a global aggregate returns a row even over no input, so it is not a test on the rows it reads (an earlier version proved `EXISTS (SELECT COUNT(*) ..)` equal to `EXISTS (SELECT 1 ..)`).

A `WHERE EXISTS` on a key the query already joins to is dropped when an inner-joined copy of that same set carries the equality. An inner join to a grouped derived table that is read only through its keys, and a `LEFT JOIN` read only through `IS NULL`, become `EXISTS` / `NOT EXISTS` (the group keys must be covered, so at most one row matches). A grouping or `DISTINCT` aggregate over a `(.. LIMIT 1)` derived table does nothing, since it sees one row, and is dropped.

Rules added from the hard-tests pass: `COUNT(DISTINCT key)` is `COUNT(key)` over one table with a declared single-column key; a `DISTINCT` projection of a left key through an inner join is `EXISTS` when every key column is NOT NULL or rejected when NULL by the join condition; an inner join to a parent is dropped when a declared foreign key, NOT NULL child columns and a parent key are all present; `COUNT(x) FILTER (WHERE GROUPING(..) = n)` over grouping sets is `COUNT(DISTINCT x)` when each filter picks exactly one set; `GROUP BY .. HAVING COUNT(*) = n` over `n` grouped branches is an `INTERSECT` of the branches; `CASE` arms that a grouped count cannot satisfy (`= 0`, or a count compared with itself) are dropped; `LIMIT` and `ORDER BY` the row count already satisfies are dropped; and two queries that qualify to the same tree are equal. The cast fold now also drops `CAST(SUM(int column) AS INTEGER)`; like the rest of the integer handling it assumes mathematical integers (no overflow). `tests/test_constraint_rules.py` replays each proof on random DuckDB data and holds the near misses.

Constructs the provers do not model are declined, never proved with the flag ignored: `FOR SYSTEM_TIME AS OF` and other time travel, `TABLESAMPLE`, `FETCH .. WITH TIES` / `PERCENT`, `OUTER APPLY`, `SYMMETRIC` ranges, `CAST .. FORMAT`, `WITH FILL`, `ASOF` match conditions (`ast_utils.check_modeled`, called by both provers after parsing). `check_modeled` does not decline `SELECT * EXCEPT`: the `Select.exclude` argument it lists is not where sqlglot keeps star modifiers (`Star.except_`, or `except` before sqlglot 30). The SMT prover applies `* EXCEPT/REPLACE/RENAME` itself and declines the cases it cannot ([provers.md](../provers.md)); the algebraic prover and the bounded checker decline a modified star. The scores above are for sqlglot 30.x; on sqlglot 26.0.0 the same suites prove fewer pairs (Calcite 177, Spark 118, TPC-H 12, TPC-C 18) because 26.0.0 parses some constructs differently, and the floors test uses those numbers there. On 26.0.0 the provers also decline aggregates that version parses as unknown functions (`BIT_AND`, `BIT_OR`, `BIT_XOR`, `MODE`, `KURTOSIS`, `REGR_*` and the like, which would otherwise read as row-level calls) and MySQL's `DIV`, which no 26.0.0 generator prints back as `DIV`. `sqlglot` is pinned below 31 until the encoders are checked against it.

`UNNEST` in `FROM` (comma or `CROSS JOIN`, optional `WITH OFFSET`) is modeled as a table of `(array, element, offset)` rows keyed by array and offset; array literals are known by their text, an array column by its value. Outer joins to an `UNNEST` stay unsupported, and no counterexample database is built for a query that unnests.

## ORDER BY, LIMIT and OFFSET

The prover compares result bags, so an `ORDER BY` matters only where a `LIMIT` or `OFFSET` cuts the sorted rows. When the ordering leaves ties, a cut may keep either of two tied rows, so the rules in `src/kumosql/limit_rules.py` move or merge cuts only when the rows that come out are the same for every way of breaking ties:

- An `ORDER BY` without `LIMIT`/`OFFSET` is dropped when nothing order-sensitive reads it (only bag operators, `IN` and `EXISTS` up to the top; never under a `LIMIT` without `ORDER BY`, a window or an `ARRAY` subquery). A key repeated in one `ORDER BY` is dropped.
- `SELECT f(c) FROM (SELECT g AS c FROM t ORDER BY o LIMIT n) AS d` is `SELECT f(g) FROM t ORDER BY o LIMIT n` at any depth, and for `OFFSET` without `LIMIT` too.
- Nested cuts on the same ordering merge: `ORDER BY o LIMIT n OFFSET m` over `ORDER BY o LIMIT k OFFSET j` is `LIMIT min(n, k - m) OFFSET j + m`. Over `UNION ALL`, a branch cut `ORDER BY o LIMIT k` with `k >= n + m` is dropped (Calcite's sort-union transpose), and so is a cut on the whole `UNION ALL` (an unparenthesized last branch's `ORDER BY .. LIMIT` parses there); a qualified key on a set operation (`ORDER BY d2.name`) is read only when its name and its place in every branch point at the same output column. Both need every output column of the outer query to be a function of its `ORDER BY` keys, so the kept rows are fixed by the sorted key values alone.
- At the top, `ORDER BY .. OFFSET m` without `LIMIT` is a cut with no limit, output columns with the same expression count as one ordering key, and with declared 32-bit integer column types `ORDER BY CAST(i AS DOUBLE)` (or `BIGINT`) is `ORDER BY i` (not for BigQuery, whose `INT` is 64-bit and does not fit a `DOUBLE` exactly).
- A `UNION` branch ending in `ORDER BY .. LIMIT` is read like a derived table with a `LIMIT`: the same text on both sides is the same rows, which is listed as an assumption.
- A cut written after a parenthesized query, `(a UNION b) ORDER BY k LIMIT 1`, is read as the cut of the whole set operation. sqlglot hangs that tail on the parentheses, not on the query inside, so unwrapping the parentheses used to drop it and both provers called the query equal to `a UNION b` (five false proofs, S027-138 to 142, issue #537). `ast_utils.merge_wrapper_tails` now folds the tail of every layer into one on the query itself (carrying a `WITH` on the parentheses with it); layers that cannot fold are declined: two layers that each cut rows, or an `ORDER BY` outside the cut, which reorders the survivors. The same holds in derived tables, CTEs, `IN`/`EXISTS` bodies and join sources, and the `((q))` collapse in `decorrelation_rules.single_value_scalar` leaves a layer with a tail alone (it moved the tail out of `x IN ((a UNION b) LIMIT 1)`). `tests/test_set_tail_soundness.py` holds the five variants and the near misses that stay proven.
- A union branch whose `WHERE` is the constant `FALSE` returns no rows whatever its source holds, so it is dropped even when the source is an opaque `ORDER BY .. LIMIT 0` cut; a union of such branches under `LIMIT 0` is then the empty query (`testSortUnionTranspose3`). A global aggregate over the same source still returns its one row, and is kept.

Pushing a `LIMIT` through a `LEFT JOIN` ordered by a non-key column (`testSortJoinTranspose1`) holds only up to ties and stays unknown, as does `LIMIT` without `ORDER BY`. `tests/test_limit_rules.py` holds the proofs and the near misses (a branch cut shorter than `n + m`, a branch `OFFSET`, the opposite direction, an ordering that leaves an output column tied). Measured against master just before they were added, these rules proved 3 more SQLSolver Calcite pairs, 1 more Spark, 4 more QED, 6 more Calcite-mined, 3 more SPES-only and 5 more VeriEQL Calcite-397 pairs, all with 0 wrong.

## Literal folding

`src/kumosql/literal_fold_rules.py` evaluates what is already decided by the query text. `UPPER` and `LOWER` of an ASCII string literal, `SUBSTRING` of a literal that starts at 1 or later and is not empty, and `CONCAT` of non-NULL string literals become the literal they give; two string literals compare exactly (`'view' = 'TABLE'` is FALSE). A start before 1, an empty result and non-ASCII case mapping are left alone because dialects disagree. A select with no grouping, aggregate, `DISTINCT`, window, `ORDER BY` or `LIMIT` over a derived table that is a `UNION` of constant rows is the `UNION ALL` of that select over each row, as long as the rows are pairwise different (numbers compare by value, so `1` and `1.0` count as one row) or the union keeps duplicates; otherwise it is left for the general path. Together they prove SQLSolver Calcite pair 53 (`UPPER(SUBSTRING(x FROM 1 FOR 2) || SUBSTRING(x FROM 3))` over three constant rows, filtered to `'TABLE'`), 224 of 232. `tests/test_literal_fold_rules.py` holds the cases and the near misses (a collapsing union, a dialect-dependent `SUBSTRING`).

## Pairs that must stay unproven

A suite's score counts the pairs a prover should prove. Two kinds of pair do not belong in that count, and they stay in the suites as guards: a proof of either one fails its test.

- Pairs a counterexample shows different: none of QED's any more (the 2 it had were a replay error, see below), 2 of R-Bot's, 1 of Cosette's (labelled equivalent, but a DuckDB database separates the converted queries) and 1 of the mined Calcite pairs. They are listed as refuted in the results files, and the suites' `scored` count (pairs minus these) is the denominator of their scores.
- Pairs that hold only if `LIMIT` without `ORDER BY` is read as a fixed tie-break: three Spark pairs (indices 50, 60 and 61 in `spark_pairs.txt`), with the reason for each in `tests/fixtures/sqlsolver/not_provable.json`. The rows a bare `LIMIT` returns are up to the engine, so proving them equal would be unsound. `tests/test_sqlsolver_benchmarks.py` fails if the prover ever proves one.
- Spark pair 44, `UPPER(LOWER(name))` against `UPPER(name)` (Spark's case-conversion simplification), listed in the same file: case maps are not inverses on Unicode text, and `UPPER(LOWER('İ'))` is `'I'` while `UPPER('İ')` stays `'İ'` in DuckDB. The random databases use ASCII names, so only this listing keeps a proof of it from passing as right; `tests/test_soundness_case_mapping.py` holds the counterexample.

Reclassifying them took them out of the denominators; measured on master fa78ff9 the scores are QED 357/373, R-Bot 36/43, Cosette 56/59, Spark 124/124 and mined Calcite 438/501. Spark is 123/123 since pair 44 joined them.

## R-Bot's Calcite pairs

`python tools/rbot_bench.py` scores the 45 (query, Calcite-rewrite) pairs shipped with [R-Bot](https://github.com/curtis-sun/LLM4Rewrite) (Apache-2.0, copied with its LICENSE to `tests/fixtures/rbot/`). Each pair is reported as `proved`, `different` (the prover failed and a random DuckDB database shows the queries disagree), `unknown`, or `wrong` (proved, yet a counterexample exists; must stay 0). R-Bot's TPC-H and DSB folders hold only template instances (same query, different constants), not rewrites, so they have nothing to score; Logos regenerated one Calcite rewrite per query for them, and those 59 pairs are scored in [Logos' TPC-H, DSB and TPC-DS pairs](logos.md). `tests/test_rbot_benchmarks.py` holds the floor. Calcite's text is read as PostgreSQL and written as MySQL (`rbot_bench.normalise`). In Calcite an `IS [NOT] TRUE/FALSE/NULL` test binds more loosely than a comparison, but sqlglot hangs it on the comparison's right operand and printed `a > b IS NOT TRUE` as `a > NOT b IS TRUE`, so the DuckDB check ran a different query; the harness now moves the test back onto the comparison and writes `NOT (a > b) IS TRUE` (`tests/test_rbot_normalise.py`).

## QED's Calcite cases

`python tools/qed_bench.py` scores the Calcite optimizer-test cases shipped with the [QED prover](https://github.com/qed-solver/prover) (MIT, VLDB 2024). QED stores them as relational-algebra JSON; `tools/qed_to_sql.py` converts 390 of the 444 to SQL (`tests/fixtures/qed/`, with QED's LICENSE). The other 54 use features the conversion cannot reproduce exactly, such as aggregate `FILTER` clauses that QED's JSON drops, geospatial functions and `LITERAL_AGG`, and are listed with a reason in `qed_calcite_skipped.jsonl`. `tools/validate_qed_pairs.py` runs both sides of every converted pair in DuckDB. Verdicts are the same four as for R-Bot, and `tests/test_qed_benchmarks.py` holds the floor.

**What the converter reads back from the plan dump.** QED's JSON drops the `OVER` clause of a window function and the grouping sets of an aggregate, but the `help` plan text it ships keeps both. The converter reads the partition and order of each window, and the grouping sets, from that text and writes `OVER (PARTITION BY .. ORDER BY ..)` and `GROUP BY GROUPING SETS (..)`; a window with a frame, several windows in one plan or a nullable ORDER BY key (Calcite and SQL engines disagree on where NULLs sort) stays skipped. Before this, the 14 grouping-set pairs were scored as plain `GROUP BY`, a query Calcite's test never runs; QED itself proves that plain reading, since its IR has no grouping sets. Pairs with grouping sets and an aggregate `FILTER` (testDistinctCountGroupingSets1 among them: QED says provable, for the query without the `FILTER`) stay skipped, now with the reason saying so. Also converted exactly: multi-column `COUNT(DISTINCT a, b)` (testAggregateJoinRemove10), `CURRENT_TIMESTAMP` as one value shared by both queries (testAggregateDynamicFunction), `ROW(..)` in the root projection as separate columns (testReduceConstants), and a projection with no columns where only the row count can matter, written `SELECT 1` (testProjectFilterTransposeRuleOnEmptyRowType and the SEMI and ANTI correlates). That brought the converted pairs from 375 to 390 and the skipped from 69 to 54.

**The two pairs QED proved and we called different.** testRightEmptyFullJoin and testStrengthenJoinType were not a QED false proof: the replay stored TIMESTAMP columns as DATE, so the pair's `CAST(hiredate AS TIMESTAMP)` turned a date into a datetime and the two sides returned `datetime.date(1994, 9, 1)` against `datetime.datetime(1994, 9, 1, 0, 0)` for the same row, a difference of storage in the harness and not of the queries (a counterexample QED's reading of the pair does not have). The replay now stores TIMESTAMP as TIMESTAMP (`sqlsolver_bench._duck_type`), and a VARCHAR or TIMESTAMP cast to its own type is an identity in `cast_rules.py`; both pairs are proved and no random database separates them. No QED proof among the 444 has a counterexample from this suite. A replay that DuckDB rejects because the pair casts text to a number is repeated on digit strings, so those pairs are checked rather than skipped.

**Rules.** `src/kumosql/dynamic_constant_rules.py` reads a column that a WHERE conjunct pins to `CURRENT_TIMESTAMP` (a timestamp column) or `CURRENT_DATE` (a date column) as that call, and drops the grouping key it becomes; `prove_equivalent_algebraic(..., statement_clock=True)` spells both queries' clock functions as one unknown constant, as QED does, and the default still refuses them (a view and its rewrite run at different times). The structural identity check (`structural_identity.py`) now also accepts a set operation, comparing the aliases of its branch selects only by position: six grouping-set pairs normalize to identical text on both sides and are proved by it. The DuckDB replay of the clock pair fixes the clock at two dates the random data can equal (`sqlsolver_bench.fix_clock`); it separates a grossly wrong pair, but is a weak check of a fine one.

**Left unknown.** Windows: testPushProjectWithOverPastJoin1, 2 and 3 are converted and not proved; window proof rules are issue #503's. The 3 count pairs with grouping sets (testPushCountNullableGroupingSetsThroughUnion, testPushCountStarGroupingSetsThroughUnion, testPushSumCountStarGroupingSetsThroughUnion) need a global `SUM` over a `UNION ALL` of per-group counts read as one count; QED does not prove the first two either. testDistinctCountMixedJoin, testDistinctCountMultipleViaJoin, testDistinctWithMultipleInputs and testDistinctWithMultipleInputsAndGroupby were skipped for a multi-column `COUNT(DISTINCT)` and now convert; QED says not provable for all four and we do not prove them. All of these new proofs were developed with the pairs in view (tuned on test).

Rules added for these suites live in `src/kumosql/keyed_rules.py`. A `GROUP BY` over one table that includes a NOT NULL key (grouped, or fixed by `WHERE k = constant`) reads each row's own value, so `SUM(x)` is `x`, `COUNT(*)` is 1 and `GROUPING(c)` is 0. A `DISTINCT` that outputs such a key is dropped in a second attempt when the first finds no proof, since dropping it on one side only can hide a match. `EXISTS` over a select made only of aggregates, with no `GROUP BY`, is TRUE. A relation that can never hold a row (`WHERE FALSE`, an empty source under an inner join or on the kept side of an outer join) makes its select empty, `EXISTS`/`IN` over it is FALSE, and a `LEFT JOIN` to it pads with NULLs (`empty_rules.py`); `ORDER BY` without `LIMIT` in a derived table is dropped. An outer join whose far side is never read is dropped under `DISTINCT` or a `GROUP BY` whose aggregates ignore duplicates (`dedup_join_rules.py`). `EXTRACT(YEAR FROM d) = 2014` (with `EXTRACT(MONTH ..)`) is the matching date range (`date_ranges.py`). QED went from 221 to 241 with these. A filter above a derived outer join that rejects NULLs from the padded side makes the join inner (`outer_filters.py`); a constant group key inlined from a derived table is dropped rather than left as a literal that would read as a column ordinal; MySQL's `CAST(x AS CHAR)` of a `VARCHAR` column is `x`; and, as a third attempt, a derived table that only removes duplicates is read without its `DISTINCT`/`GROUP BY` under a duplicate-blind select (`dedup_join_rules.strip_distinct_sources`). QED reached 266 and Spark 121 with these.

Quantified subqueries live in `quantified_rules.py`. `x op ANY (q)` (or `SOME`) and `x op ALL (q)` are written with `EXISTS`, keeping SQL's three-valued result: ANY is TRUE when some row of `q` compares TRUE, FALSE when every row compares FALSE (so an empty `q` gives FALSE, and ALL over it TRUE), NULL otherwise. In a WHERE, HAVING or ON condition only TRUE (or, under NOT, FALSE) matters, so one `EXISTS` stands for the test; elsewhere it is a `CASE` over two `EXISTS` tests. `= ANY` is `IN`, `<> ALL` is `NOT IN`, and `NOT (x op ANY q)` is `x <negated op> ALL q`. Calcite removes such subqueries by joining a one-row aggregate of `q` (`MIN`/`MAX`, `COUNT(*)`, `COUNT(y)`, and for `IN` a TRUE indicator LEFT JOINed on `x = y`) and reading it in a three-valued condition. A condition that reads those columns is folded back to `x op ANY/ALL (q)` or `x IN (q)` only when z3 proves it gives the same TRUE, FALSE or NULL as the subquery test for every possible state of the aggregates (or the same TRUE/FALSE where only that matters), with NOT NULL and key facts about `x` and `y`; anything else is left as written. The same check reads Calcite's constant `c IN (q)`, the first row of `(y IS NOT NULL, COUNT(*))` grouped over the rows of `q` where `y = c OR y IS NULL` (ordered TRUE first, `LIMIT 1`), as `c IN (q)`; an indicator grouped by `y, TRUE` counts as grouped by `y`. A correlated `q` is expanded with `LEFT JOIN LATERAL (...) ON TRUE`: the indicator then filters its rows on `x = y` inside the LATERAL body, and joins at most one row when `y` is grouped or a key; the probe may carry only the `y IS NOT NULL` group. Both fold the same way; this added three mined Calcite pairs (429 to 432, one of them the held-out testExpandProjectInWithTwoCorrelatedSubQueries, so 113 to 114 new pairs) and one QED pair (354 to 355), measured on master e5ccdcf. Calcite also decorrelates ANY by grouping the subquery on its correlation key. QED's plans LEFT JOIN those groups on the key, and the mined plans join a domain of the outer key values first (`SELECT DISTINCT k FROM outer` LEFT JOINed to the groups with `IS NOT DISTINCT FROM`). `domain_join_rules.py` rewrites each of these as a `LEFT JOIN LATERAL` one-row aggregate over the rows with `k = o.k`. Each column takes `CASE WHEN COUNT(*) = 0 THEN NULL ELSE ... END` where a missing group would have left it NULL. A domain join is rewritten only when the outer key is NOT NULL and read from a real row of the same table the domain lists in full. The fold above then reads these columns, wrappers included, through z3, and a rewrite that no fold uses is undone. `tests/test_domain_join_rules.py` checks every rewrite and proof against DuckDB, using generated plans, mutations and hand-written pairs from outside research whose labels were re-checked on DuckDB (8 of those labels were wrong). `tests/test_quantified_rules.py` checks the EXISTS form on random NULL-bearing DuckDB data and checks that faithful expansions are proved while deliberately broken ones never fold into a different query. On top of the false-proof fixes these rules took QED from 251 to 258, the mined Calcite pairs from 279 to 294 (held-out 58 to 63) and SQLSolver's Calcite set from 213 to 214, with 0 wrong; the constant `IN` reading added one more pair to each of QED and the mined Calcite pairs.

Derived tables that hold an outer join are read through (`src/kumosql/outer_join_flatten.py`). The prover keeps such a table whole and compares it by text, so Calcite's plans, which wrap every outer join in projection layers, never met the flat form. A select whose FROM item is that derived table reads the join itself, with the derived columns written as their expressions and the derived WHERE added to its own; joins after it extend the flattened join, and a grouped select is re-wrapped in the canonical positional form. Where a later RIGHT or FULL join could pad the derived table, it must not filter and every column read must be NULL on the padded row. A computed column of a derived outer join that another join reads (`a JOIN (SELECT f(b.x) AS y FROM b LEFT JOIN c ..) d`) is computed above it instead, which on the NULL-extended side is allowed only for expressions that are NULL when their inputs are (`null_when_inputs_null`: arithmetic, comparisons, a `CASE` whose reachable arms are NULL; never constants, `IS NULL` or `COALESCE`). Its plain columns are listed in a fixed order (by source, then name), and the LEFT JOIN indicator test is tried again once flattening has brought it next to its `IS NULL` test. A lone `RIGHT JOIN` is written as the mirrored `LEFT JOIN`, a `FULL JOIN` with an empty side becomes one-sided, and a parenthesized inner join tree (`a JOIN (b CROSS JOIN c) ON p`) is read left-deep; an outer join to a tree is not, since that would change which rows are padded. A column that its derived table fixes to a number (`WHERE empno = 10`) reads as that number in a later outer join's ON clause, unless an earlier join could have padded that table with NULLs. A `LEFT JOIN` whose WHERE compares a column of the padded side is an inner join, the flat form of `outer_filters.py`'s rule. `tests/test_outer_join_flatten.py` proves each rule's cases and checks them on random DuckDB data, next to near-miss pairs that differ and must stay unproven.

`ROLLUP`, `CUBE`, MySQL's `WITH ROLLUP` and mixed lists such as `GROUP BY a, ROLLUP(b, c)` are spelled out as one `GROUPING SETS` list (the cross product of each element's sets), and each set becomes one branch of a `UNION ALL` (`grouping_sets.py`). A key missing from a set reads as NULL only in that branch's own select list and `HAVING`; its sources, `WHERE` and aggregate arguments keep the key's value. The empty set `()` is one row even without an aggregate. A list that repeats a set, or spells out more than 64 sets, is left alone, since engines disagree on whether a repeated set repeats its groups. A `HAVING` condition on grouping keys alone moves to `WHERE` when there is at least one key (`having_rules.py`). For windows (`window_rules.py`): a column that every branch of a `UNION ALL` computes as the same expression of the same table column is computed after the union instead, so a window over Calcite's pushed-down projection reads like the original; and `c IS NULL` is FALSE when `c` is a derived table's `COUNT` (windowed or not). A windowed derived table, which the prover keeps whole and matches by its text, lists its outputs by their text, and a derived `UNION ALL` lists its columns by what the branches compute rather than by name (unless a `*` reads them in order).

Two false proofs were fixed with this work: `GROUPING SETS ((a), ())` without an aggregate used to read its `()` branch as one row per input row, and a global `SUM` of a derived table's `COUNT(*)` was read as `COUNT(*)`, which differs over no rows (NULL against 0) unless wrapped in `COALESCE(.., 0)` or `NULLIF(.., 0)`. A derived `UNION ALL` of named columns now drops the columns the query around it never reads, as the same union of `SELECT *` already did.

Casts, constants and join syntax (`cast_rules.py`, failing-tests cluster 10): a cast that cannot change a value is dropped. That covers an integer expression cast to `INT` or a wider integer type (`CAST(SUM(sal) AS INTEGER)`, `CAST(1 AS BIGINT)`; overflow is excluded as elsewhere, and a cast to `TINYINT` or `SMALLINT` folds only when the input is declared that narrow), a DATE cast to DATE, a boolean cast to BOOLEAN, `CAST(CAST(x AS T) AS T)`, and a literal that fits its target exactly (`CAST('12' AS SIGNED)` is 12, `CAST(5 AS DECIMAL(11, 1))` is 5.0). Types come from the declared column types, read in the query's dialect (every BigQuery integer type is `INT64` and every Snowflake one `NUMBER(38, 0)`, whatever its name; a declared `INT8` is never read as an 8-bit integer), and are followed through derived tables. An `INT` cast to `DOUBLE` keeps its order, so it is dropped from an `ORDER BY` key (a cast to the 32-bit `FLOAT` only for integers of at most 7 digits, since 16777217 is not a `FLOAT`, and a `FLOAT(p)` never); there the size of arithmetic is bounded from its operands' sizes rather than read as their width (`i * i` of two `INT`s can need 19 digits), and a `SUM` keeps its cast. `lit IS NULL` and constant `CASE` conditions fold, `ROUND(x)` is `ROUND(x, 0)`, and `COUNT(x) > 1` is `COUNT(x) >= 2`. Other integer comparisons stay as written, because the SMT reads numbers as reals. `1 * x` is `x` where `x` is already a number or is read as one, but only in dialects whose `/` never divides integers to an integer. `NATURAL JOIN` is read as `USING` over the shared column names. `USING` over a derived table is read once the table's stars are known, and `SELECT *` over a `USING` join lists the merged column once, first. Measured against master just before merging, QED went from 297 to 307, Calcite-mined from 348 to 356 (held-out 78 to 80, two of them read while developing), SPES-only from 27 to 29 correct, VeriEQL Literature from 15 to 18, VeriEQL Calcite-397 from 247 to 255 and Singh & Bedathur from 2,581 to 2,586, all with 0 wrong.

Correlated subqueries and `LATERAL` joins are brought to shapes the prover already decorrelates by `src/kumosql/decorrelation_rules.py`. A filter-and-project derived table that reads the enclosing query (`FROM (SELECT .. FROM t WHERE t.k = o.k) AS d` inside an `IN`, `EXISTS` or scalar subquery) is merged into its reader, so the correlation sits in the reader's `WHERE`. A `LATERAL` body that reads nothing from the query is a plain derived table, and `CROSS JOIN LATERAL` is `INNER JOIN LATERAL .. ON TRUE`. An inner join to a body that returns one constant row when its input has a row (`SELECT TRUE .. GROUP BY TRUE`) is `WHERE EXISTS`. A `LATERAL` DISTINCT set (`GROUP BY` of its one output) joined by `v = d.c` and read nowhere else is `v IN (..)`; a filter over a projection that holds the lateral join moves inside first. A global aggregate that reads nothing from the query, joined `ON TRUE` (inner or `LEFT`), is read as the scalar subquery (an inner join whose `WHERE` reads the aggregate stays a join, which the prover reads better), and `(SELECT SINGLE_VALUE(x) ..)` is `(SELECT x ..)`. The row itself witnesses `EXISTS (SELECT .. FROM t AS y WHERE y.c = x.c)` over its own table (`=` on a NOT NULL column, or `<=>`), so that test is TRUE. Tests on the compared column inside an `IN` body (`x IN (SELECT c FROM t WHERE c IN q AND NOT c IN r)`) move out to `x`, and `x IN (SELECT c FROM t)` is dropped next to `x IN (SELECT c FROM t WHERE ..)`. `MAX` over the top rows by that column descending, NULLs last (`ORDER BY x DESC LIMIT n`, `n >= 1`) is `MAX` over all of them (`MIN` ascending alike). A comparison with a NULL literal in `WHERE` makes it FALSE. A `DISTINCT` derived table joined on all its columns may now be pinned to `+ - *` expressions over outer columns the join requires to be non-NULL, not only to plain columns.

DISTINCT and regrouping rules live in `src/kumosql/distinct_rules.py`. A membership test (`IN`, `NOT IN`, `EXISTS`) only sees which values occur, so a `DISTINCT` or key-only `GROUP BY` inside it is dropped. A `DISTINCT` (or key-only `GROUP BY`) derived table read by a query that keeps only distinct rows, or aggregates with `MIN`, `MAX` or `DISTINCT` only, needs no deduplication of its own, through outer joins too: whether a row finds a partner depends only on which rows exist. A plain `DISTINCT` select over a grouped derived table folds into that grouped select (its `WHERE` joins the `HAVING`). An aggregate over a finer grouping folds into one aggregate: `SUM(x)` over `GROUP BY x` rows is `SUM(DISTINCT x)`, `SUM` of partial sums is the sum, `COALESCE(SUM(count), 0)` is the count (a bare `SUM(count)` only under `GROUP BY`, since a global aggregate over no rows is NULL), with or without an outer `GROUP BY`, and an extra key fixed by `key = constant` does not split a group. An inner join with a `DISTINCT` derived table equated on all of its columns and read nowhere else is an `EXISTS` test. `SELECT DISTINCT` over groups that outputs every group key drops the `DISTINCT`, `DISTINCT(a)` reads `a`, and `CAST(COUNT(..) AS BIGINT)` is the count. Measured against master just before they merged (#379), they added 5 QED proofs, 4 R-Bot, 1 Cosette, 2 Calcite-mined (gaining 2 held-out pairs and losing 3, not investigated), 12 VeriEQL Calcite-397, 1 Literature and 21 Singh & Bedathur, with 0 wrong. A source's deduplication is kept when its reader has an unqualified column that is not one of its outputs, since merging the source in could make that column name the source's table instead of an outer query's. `tests/test_aggregation_pushdown_pairs.py` holds 28 aggregation and DISTINCT pushdown pairs from an outside review (eager aggregation, partial-aggregate merging, DISTINCT over `UNION ALL`, outer-join empty sides): each of the 18 that differ has a witness database re-run on DuckDB with its optimizer off and must never be proved, and the 10 equivalent ones must agree on random databases.

**Splits.** The held-out split is the pairs new to every other corpus (`new` in the fixture, 168), the dev split the 334 that SQLSolver, QED or R-Bot hold. `--split dev` scores only the dev pairs and is the one to develop on; `--split held-out` scores only the held-out ones; `--split all`, the default and the published command, scores every pair and prints the held-out pairs' count on its own (`new to every other corpus: X/Y proved`), which is the results file's `held_out`. As the history above says, many held-out pairs were read while rules were written, so that score is tuned on test.

Set-operation rules (`src/kumosql/setop_rules.py`): a duplicate-removing `UNION`, `INTERSECT` or `EXCEPT` of two selects of the same table with the same output becomes one `SELECT DISTINCT` with the filters combined (`OR`; `AND`; `AND NOT COALESCE(q, FALSE)`), which for `INTERSECT` and `EXCEPT` needs a filter that reads only output columns; other `INTERSECT`/`EXCEPT` pairs become `EXISTS`/`NOT EXISTS` tests with null-safe `<=>` matching. Before this, a parenthesized `INTERSECT` or `EXCEPT` operand in a derived table was mistaken for a scalar subquery and failed to parse.

The same module holds bag identities for set operations, each kept only when it holds on every database: `X EXCEPT [ALL] X` is empty (aliases and integer casts of small literals ignored; never with `RAND()`, windows or `LIMIT`); `X EXCEPT ALL` an empty query is `X`, and `EXCEPT` one is `SELECT DISTINCT` of `X`; `INTERSECT ALL` with an operand that has no repeated rows (DISTINCT, grouped by exactly its outputs, a global aggregate) is `INTERSECT`, and so is `EXCEPT ALL` when the left operand has none; a select that passes every column of a derived set operation through unchanged is that set operation, and with `DISTINCT` over `UNION ALL` or `INTERSECT ALL` it is the duplicate-removing form (never over `EXCEPT ALL`, whose `DISTINCT` is not `EXCEPT`); a duplicate-removing set operation drops a `GROUP BY` from an operand that groups by exactly its outputs and computes nothing. Measured against master: SQLSolver Calcite 215 to 216, QED 309 to 315, mined Calcite 357 to 370 (85 of the 168 new pairs, up from 80), VeriEQL Literature 18 to 20 proved; Spark, Cosette, SPES and R-Bot unchanged. `tests/test_setop_rules.py` checks each identity, and each near miss, on random DuckDB data as well as by proof.

Rules from the dev-split unknowns (QED and the 334 mined pairs other corpora share): `grouped_sums.drop_grouped_sum_coalesce` reads `COALESCE(SUM(x), 0)` in a grouped select as `SUM(x)` when every branch computes `x` as a `COUNT`, a literal or a NOT NULL column (Calcite's COUNT pushed through `UNION ALL`); `lone_source.lift_derived_expressions` moves expressions a derived outer join computes up into the grouped select that reads it, so a projection pushed below an outer join meets the unpushed one; and the left-join indicator (`LEFT JOIN (.. TRUE AS i ..) .. i IS NOT NULL`) and select-list `IN` are now read as `EXISTS` through projection-only derived tables.

## Cosette and SPES fixtures

`tests/fixtures/cosette/` holds 60 pairs converted from [Cosette](https://github.com/uwdb/Cosette)'s examples (BSD-2-Clause) by `tools/cosette_to_sql.py`: equivalent, not-equivalent and conditionally equivalent (under primary keys) cases, with uninterpreted predicates as hidden Boolean columns. `tests/fixtures/spes/` holds the 34 runnable [SPES](https://github.com/georgia-tech-db/spes) Calcite pairs (Apache-2.0) whose text differs from SQLSolver's Calcite pairs (`tools/spes_to_sql.py`). `tests/fixtures/calcite_overlap.json` (`tools/calcite_overlap.py`) lists which corpora (SQLSolver, SPES, Cosette, R-Bot, QED) hold each Calcite test. `tests/test_cosette_fixtures.py` checks they parse and run.

`python tools/cosette_bench.py` scores them (`tests/test_cosette_benchmarks.py` holds the floors). Cosette: 59/59 correct, 0 wrong (54 equivalent pairs proved, all 5 not-equivalent pairs refuted with a DuckDB counterexample, 0 unknown; `testDecorrelateTwoIn` is refuted against its label, a transcription issue in Cosette's file). It was 56/59 until `keyed_set_join.py` (S019, measured on master 884470c) proved `ex1sigmod92`, `ex2sigmod92` and `ex2sigmod92simpl`; that rule was written with those pairs in view (tuned on test), no held-out pair exists for this suite, and no proof was lost. SPES-only: 34/34 correct, 0 wrong (31 proved, 30 before S019's counted-membership rule proved `testWhereNotInCorrelated`; 29 before batch 1's set-operation ORDER BY key reading proved `testSortUnionTranspose`, a pair it was written against, measured on master 45533e5; 26 before the ORDER BY, LIMIT and OFFSET rules; all 3 pairs relabelled not equivalent are refuted). Before scoring, the harness spells a table one way across a pair when its two sides spell it in different case (`A` and `a`, one table for Cosette) and spells out `SELECT *` over a join with a repeated column inside a derived table (`tools/bench_sql_repairs.py`). A pair the plain random search does not separate is tried again with the prover's own counterexample, re-run in DuckDB, and with `kumosql.counterexample`'s stronger search; only executed differences count. Every Cosette and SPES test name is already in SQLSolver's set; they add other wordings of the same tests, not new tests. Across all corpora there are 430 distinct Calcite test names, 174 of them only in QED. See the READMEs in those folders for translation rules, labels and skips.

Bounded verification (3 rows per table, [bounded-verification.md](bounded-verification.md#results)) agrees on the same pairs: Calcite 212/232, Spark 106/127, TPC-H 7/22 (date literals and large joins), TPC-C 19/19, QED 363/375, R-Bot 23/45, Cosette 52/60 plus 6 refuted, SPES 26/34 plus 3 refuted, 0 wrong. It is a separate evidence level, not a proof.

### Adapted Cosette pairs

Four of Cosette's `sqlrewrites` files are skipped from the 60 because a table has no declared columns (`schema s(??)`): `SelfJoin0`, `productDistributesOverUnion`, `projectionDistributesOverUnion` and `pushdownSelect`. `tests/fixtures/cosette/cosette_adapted.jsonl` writes each one with two declared `INTEGER NOT NULL` columns per table (a bare `(r union all s)` in `FROM` becomes a derived table; `pushdownSelect`'s predicate `b` is the hidden column `__b`, as in the conversion) and adds not-equivalent siblings written here: `SelfJoin0` without `DISTINCT` (n rows give n*n on one side and n on the other), `SelfJoin0` joined to another table (an empty partner empties one side only), `UNION` in place of `UNION ALL` for both distributivity files, and `pushdownSelect` with the filter pushed into the wrong input (a concrete `= 1`, since refutations of hidden-predicate pairs are never claimed). Each pair records its source file, the file's SHA-256 at the pinned commit and how it was adapted.

`python tools/cosette_bench.py cosette-adapted` scores them apart from the original pairs, so the Cosette score above is unchanged (results file `cosette-adapted`): **9/9 correct, 0 wrong**: 4 equivalent pairs proved (`SelfJoin0` included, which holds on an empty `r` too) and all 5 siblings refuted with a counterexample executed in DuckDB with its optimizer off. That was the baseline; no prover change was made for these pairs. One pair in five by SHA-1 of its name is held out: `SelfJoin0` and `projectionDistributesOverUnion`, both proved (2/2). A proof covers the two-column instance, not every schema `s(??)` stands for. The other 22 skipped files are not adapted: their skips are about the source text (empty `(VALUES)`, keys the file does not declare, type mismatches, preconditions not stated, two-row predicates), not a missing column list.
