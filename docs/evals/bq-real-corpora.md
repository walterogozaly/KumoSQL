# Real BigQuery projects

Every other syntax eval runs SQL written for it. This one runs code people wrote for their own projects: open-source Dataform projects and BigQuery SQL, copied at pinned commits with their licences into `tests/fixtures/bq_corpora/`. No language model runs at evaluation time.

`python tools/bq_corpus_bench.py [--json out.json] [--write-results]`. The floors are in `tests/test_bq_corpus_bench.py`, and the scoreboard row is `benchmarks/results/bq-real-corpora.json`. To refresh the copies, run `python tools/fetch_bq_corpora.py [--only NAME]`; it reads `tests/fixtures/bq_corpora/sources.json`, which pins each project's commit.

From bigquery-utils, the `udfs/` folder belongs to the UDF behaviour eval, and the other two Dataform examples hold no SQL (assertions written in JavaScript, and a tutorial). Nothing here overlaps another eval's SQL: the Stack Overflow data is also SQLStorm's and Spider 2.0's subject, but their queries are different.

## What is scored

| | Measure |
| --- | --- |
| Correctness | Must all be 0: crashes while loading, cleaning up or formatting; a cleanup or format change accepted without a proof; a backticked name changed; a literal `${ref("x")}` or config dependency missing from the graph |
| Coverage | Statements read and columns traced in query models; files read with no blocking gap and also cleaned up and formatted without one; the gaps the loader reports, by kind |
| Held out | A fifth of the files, chosen by SHA-1 of `project/path`, scored apart |
| Performance | Seconds for every project and stage |

## Bugs found and fixed

1. A statement after a header comment of more than about 600 characters was not recognised. The script reader looked at the first 600 characters of the text, comments included, to decide what kind of statement it was, so a long licence header hid a `CREATE VIEW`. All 40 basedosdados views were left unread (0/40 statements, 0 columns). Now 40/40 are read and 923/923 columns traced.
2. The unparsed-operations message counted the statements of a called procedure against the calling file, giving "7 of 1 operations statements could not be read". Statements inside called procedures are now counted on their own.
3. A `ref()` whose arguments hold a call, `${ref({schema: functions.baseSchema("ga4"), name: "event"})}` or `${ref(functions.baseSchema("ga4"), "event")}`, was not recognised and was masked like any other template, so 35 marketing-jumpstart refs were not edges. A config `schema:` or `database:` computed by JavaScript fell back to the project default, so two actions named `event` in the base and product datasets collided and one replaced the other (4 models lost). Now a computed dataset or project is the variable's value when it is `dataform.projectConfig.vars.x` (from `workflow_settings.yaml` or `dataform.json`), and otherwise a placeholder spelling the expression, such as `{functions:baseSchema("ga4")}`, when the expression is a global (`dataform` or an `includes/` module) called with literals at most. Actions with different expressions stay apart, a ref written with the same expression finds its action, and a ref whose computed dataset matches no action of that name while actions of that name exist elsewhere is left unresolved rather than guessed. marketing-jumpstart went from 35 failures to 3, from 22/57 to 57/60 dependencies, and from 217 to 239 columns traced.
4. `WHERE ${when(incremental(), `ts >= checkpoint AND`)} ts >= ...`, a `when()` that ends with the connective of the condition it opens, was masked as `WHERE __sqlx_token__ ts >= ...`, which does not parse: 17 security-analytics summaries were read from their tokens only. The mask is now `__sqlx_token__ AND`, and a rewrite that parts the two can no longer be restored (it is refused rather than restored elsewhere). security-analytics went from 89/106 to 106/106 statements and 446 to 622 columns traced.
5. Reading the tables of an unparsed statement from its tokens took the `FROM` of `EXTRACT(DATE FROM timestamp)` for a table, so those 12 summaries reported a read of an external table `timestamp`. A `FROM` inside `EXTRACT`, `TRIM`, `SUBSTRING`, `SUBSTR`, `OVERLAY` or `POSITION`, or after `IS [NOT] DISTINCT`, no longer names a table.

## What is left

- **Tables published by JavaScript** (the 3 failures). marketing-jumpstart publishes `location`, `device_type` and `normalized_device_type` from `.js` files with `publish("location", {schema: functions.baseSchema("ga4"), ...})`. KumoSQL does not run that JavaScript, so the actions are not graph nodes and the refs to them are not edges; they are listed in `KNOWN_MISSES` in the test.
- **JavaScript in SQLX** accounts for most other gaps. Snowplow names its tables with constants from `includes/sp.js` (`${sp.scratch_schema}`), giving 57 `unresolved_template` gaps, and splices SQL returned by JavaScript functions into a condition or a `BEGIN ... END` block, giving 7 `parse_error` gaps; their table reads still come from the tokens. marketing-jumpstart builds its Google Ads views with `functions.buildAdsViewUnion(...)` (10 `unresolved_template`). One wintermi action and one marketing-jumpstart table are built entirely by JavaScript (`no_query`).
- **Operations that write the tables their readers read.** marketing-jumpstart's `update_dim_ads` reads `dim_ads` and its post-operations `UPDATE` and `INSERT` into it, which the graph reports as 11 `cycle` gaps.
- **`SELECT *` over tables with unknown columns** (22) and reads of tables outside the project (48, mostly basedosdados staging tables and the audit-log export) are reported, not guessed.
- **Speed on very large statements.** Formatting and cleaning up `bigquery_audit_logs_v2.sql` (51 KB) and `bigquery_script_logs_v2.sql` (37 KB) take about 50 s each per stage, almost all of it in sqlfluff. The test therefore only loads and traces `bqutils-views`; the bench runs every stage.
- Nothing is run on BigQuery, so values are not compared.
