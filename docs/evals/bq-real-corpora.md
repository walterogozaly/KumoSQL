# Real BigQuery projects

[Plain-language version](../../docs_simple/evals/bq-real-corpora.md)

Every other syntax eval runs SQL written for it. This one runs code people wrote for their own projects: open-source Dataform projects and BigQuery SQL, copied at pinned commits with their licences into `tests/fixtures/bq_corpora/`. No language model runs at evaluation time.

`python tools/bq_corpus_bench.py [--json out.json] [--write-results]`. The floors are in `tests/test_bq_corpus_bench.py`, and the scoreboard row is `benchmarks/results/bq-real-corpora.json`. To refresh the copies, run `python tools/fetch_bq_corpora.py [--only NAME]`; it reads `tests/fixtures/bq_corpora/sources.json`, which pins each project's commit and the SHA-256 of the files kept (`python tools/fetch_bq_corpora.py --check` recomputes it from the copies on disk, and `tests/test_bq_corpus_bench.py` runs that check). All thirteen licences (Apache-2.0 and MIT) allow the copies, and each folder keeps its own `LICENSE`; a source with no licence, a GPL one or NC/SA terms would be downloaded at run time from its pinned commit instead of committed.

| `wintermi-imdb`, `-bqe`, `-fashion`, `-movielens` | wintermi/*-dataform (Apache-2.0) | Current Dataform layout (`workflow_settings.yaml`), INFORMATION_SCHEMA jobs, SQL generated by JavaScript |

| `basedosdados` | basedosdados/sdk, `bases/*/*/publish.sql` (MIT) | `CREATE VIEW` over dashed project names, `SAFE_CAST`, long header comments (a 40-file sample of 536 near-identical files, renamed after their folders) |
| `dataform-stackoverflow` | dataform-co/dataform-example-project-bigquery (MIT) | Dataform's own example: sources, staging and reporting layers over the Stack Overflow public data |
| `marketing-jumpstart` | GoogleCloudPlatform/marketing-analytics-jumpstart-dataform (Apache-2.0) | GA4 and Google Ads layers whose datasets are computed by JavaScript (`functions.baseSchema("ga4")`), refs with computed datasets, actions published from `.js` files, `UPDATE`/`INSERT` post-operations |

| `bqutils-views` | GoogleCloudPlatform/bigquery-utils, `views/` (Apache-2.0) | Audit-log views of 37 to 51 KB in one statement, JSON extraction, a Teradata calendar view (the five `.sql` files that folder holds) |
| `bqutils-datavault` | GoogleCloudPlatform/bigquery-utils, `dataform/examples/dataform_datavault` (Apache-2.0) | Data Vault hubs, links and satellites with hash keys built by JavaScript |

The dbt projects (ga4-bigquery-starter, bigquery-dbt-user-dimension, dbt-ga4) are left out: their SQL is Jinja, which KumoSQL does not render. From bigquery-utils, the `udfs/` folder belongs to the UDF behaviour eval, and the other two Dataform examples hold only JavaScript (unit-test assertions) and Markdown, so there is no SQL to load. Nothing here overlaps another eval's SQL: the Stack Overflow data is also SQLStorm's and Spider 2.0's subject, but their queries are different. The five projects added last (the last five rows, `dataform-stackoverflow` to `bqutils-datavault`) are scored with a baseline and a held-out fifth, below.

## What is scored

| | Measure |
| --- | --- |
| Correctness | Must all be 0: crashes while loading, cleaning up or formatting; a cleanup or format change accepted without a proof; a backticked name changed; a literal `${ref("x")}` or config dependency missing from the graph |
| Coverage | Statements read and columns traced in query models; files read with no blocking gap and also cleaned up and formatted without one; the gaps the loader reports, by kind |
| Held out | A fifth of the files, chosen by SHA-1 of `project/path`, scored apart |
| Performance | Seconds for every project and stage |

The first eight projects score exactly as on master before the five were added (202 files, 120/121 statements, 1,359/1,371 columns, 129 handled): none of the changes below moves one of their numbers.

**Baseline of the five added projects, on master before any fix:** 183 files, 35 failures, all in `marketing-jumpstart` (35 literal refs not in the graph); dependencies 150/185; statements 146/169; columns 924/1,006; 99 files handled. Per project: `marketing-jumpstart` 22/57 dependencies, 41/47 statements, 217/279 columns, 6 handled, with 4 `duplicate_model` gaps; `security-analytics` 89/106 statements, 446/461 columns, 78 handled, 17 `parse_error` gaps and 12 false reads of a table called `timestamp` (`external_tables`); `bqutils-views` 3 handled; the other two as now. **After the fixes:** 3 failures; dependencies 185/188; statements 167/173; columns 1,122/1,225; 107 handled. `marketing-jumpstart` reads more (45 statements, 239 columns, 57 dependencies) but is handled less (3 files, was 6): the models it could not tell apart before are now all read, and each one carries a gap that blocks (`dynamic_config` on 53 of them, a computed dataset, and 11 `cycle`).

**Held out:** of the 58 files in the hash-chosen fifth, 35 are handled and 1 has a failure (`marketing-jumpstart`'s `normalized_device.sqlx`). In the five added projects that is 15/28 handled and 1 failure, against 14/28 and 6 failures at the baseline. This is not a clean hold-out: the loader bugs were found and fixed with every file's failures in view, held-out files included (**tuned on test**), so the fifth shows only that the fixes did not break files they were not aimed at. The first eight projects were never held out.

A cleanup rule leaves a statement that holds a JavaScript constant such as `${sp.output_schema}` or `${sp.entropy}` as written, and when a rule or override changes one anyway, the [proof safeguards](../proof-safeguards.md#dataform-expressions) keep the change `unproven` until the SQLX is compiled, because the constant can expand to any SQL. The two wintermi `template_columns` gaps, which take the handled count from 131 to 129, came from a loader change on master, not from the safeguards.

## Bugs found and fixed

1. A statement after a header comment of more than about 600 characters was not recognised. The script reader looked at the first 600 characters of the text, comments included, to decide what kind of statement it was, so a long licence header hid a `CREATE VIEW`. All 40 basedosdados views were left unread (0/40 statements, 0 columns). Now 40/40 are read and 923/923 columns traced.
2. The unparsed-operations message counted the statements of a called procedure against the calling file, giving "7 of 1 operations statements could not be read". Statements inside called procedures are now counted on their own.
3. A `ref()` whose arguments hold a call, `${ref({schema: functions.baseSchema("ga4"), name: "event"})}` or `${ref(functions.baseSchema("ga4"), "event")}`, was not recognised and was masked like any other template, and a config `schema:` computed by an `includes/` function fell back to the project default, so two actions named `event` in the base and product datasets collided and one replaced the other (4 models lost). 35 marketing-jumpstart refs were not edges. Now such a dataset is a placeholder that spells the expression (`{functions:baseSchema("ga4")}`), the action keeps its `dynamic_config` gap, a ref written with the same expression finds its action, and a ref whose placeholder matches no action of that name is left unresolved rather than guessed ([details](../dataform-repositories.md)). A `publish()` call in a `.js` file with such a schema is listed too, so its file no longer makes every unlisted name unknowable (`unsupported_ref` gaps 8 to 2). marketing-jumpstart went from 35 failures to 3, from 22/57 to 57/60 dependencies, and from 217 to 239 columns traced.
4. `WHERE ${when(incremental(), `ts >= checkpoint AND`)} ts >= ...`, a `when()` that ends with the connective of the condition it opens, was masked as `WHERE __sqlx_token__ ts >= ...`, which does not parse: 17 security-analytics summaries were read from their tokens only. The mask is now `__sqlx_token__ AND`, and a rewrite that parts the two can no longer be restored (it is refused, not restored elsewhere). security-analytics went from 89/106 to 106/106 statements, 446 to 622 columns traced, and 17 to 0 `unsupported` cleanups.
5. Reading the tables of an unparsed statement from its tokens took the `FROM` of `EXTRACT(DATE FROM timestamp)` for a table, so 12 summaries reported a read of an external table `timestamp`. A `FROM` inside `EXTRACT`, `TRIM`, `SUBSTRING`, `SUBSTR`, `OVERLAY` or `POSITION`, or after `IS [NOT] DISTINCT`, no longer names a table.

## What is left

- **Tables published by JavaScript** (the 3 failures). marketing-jumpstart publishes `location`, `device_type` and `normalized_device_type` from `.js` files with `publish("location", {schema: functions.baseSchema("ga4"), ...}).query(ctx => ...)` and a query KumoSQL does not read out of the file. The refs to them now resolve to the right table, which is reported as read from outside the project (`external_tables`), but the actions are not graph nodes, so the refs are not edges. They are listed in `KNOWN_MISSES` in the test.
- **JavaScript in SQLX** accounts for most other gaps. Snowplow names its tables with constants from `includes/sp.js` (`${sp.scratch_schema}`), giving 57 `unresolved_template` gaps. It also splices SQL returned by JavaScript functions into a condition or a `BEGIN ... END` block, giving 7 `parse_error` gaps. Their table reads still come from the tokens. marketing-jumpstart has 9 `unresolved_template` gaps of its own. One wintermi action and one marketing-jumpstart table are built entirely by JavaScript (`no_query`). One terashim declaration takes its database and schema from `includes` constants, so it is reported once as `dynamic_config`; refs still find it by name and the project defaults stand in for its location. The 53 marketing-jumpstart `dynamic_config` gaps are its computed datasets: the placeholder keeps the actions apart, but the table they write is still only known by running the project.
- **Operations that write the tables their readers read.** marketing-jumpstart's `update_dim_ads` reads `dim_ads` and its post-operations `UPDATE` and `INSERT` into it, which the graph reports as 11 `cycle` gaps.
- **`SELECT *` over tables with unknown columns** (22), `template_columns` (25, `${...}` text that may name columns) and reads of tables outside the project (49, mostly basedosdados staging tables and the audit-log export) are reported, not guessed.
- **Speed on very large statements.** Formatting and cleaning up `bigquery_audit_logs_v2.sql` (51 KB) and `bigquery_script_logs_v2.sql` (37 KB) take about a minute each per stage, almost all of it in sqlfluff. The test therefore only loads and traces `bqutils-views`; the bench runs every stage.
- **No clean hold-out.** The five added projects were fixed against with their held-out files in view (tuned on test). A later source of the same kind should keep its fifth unread until the baseline is recorded.
- Nothing is run on BigQuery, so values are not compared.
