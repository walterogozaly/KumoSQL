# Running BigQuery SQL on DuckDB

[Plain-language version](../docs_simple/bigquery-on-duckdb.md)

Every refutation KumoSQL reports from execution runs BigQuery SQL on DuckDB after sqlglot translates it: the counterexample searches (`kumosql.executed_refutation`, `kumosql.refute`, `kumosql.counterexample`), the bounded checker's replay, random databases (`kumosql.random_check`), synthetic-data comparison (`kumosql.result_equivalence`) and incremental-model simulation. Where the two engines read the same SQL differently, a DuckDB difference can be a false BigQuery refutation, which is a wrong answer. `src/kumosql/bigquery_on_duckdb.py` closes those gaps for every BigQuery-dialect run; SQL read in other dialects (MySQL, Postgres, SQLite, DuckDB evals) is run as before.

It does three things.

**Session settings** (`configure(connection)`): timestamps are read in UTC whatever the machine's zone. NULL order needs no setting: sqlglot writes BigQuery's (`NULL` first ascending, last descending) against DuckDB's default, spelling `NULLS FIRST` where the two differ and leaving `ASC NULLS LAST` bare, so a session default would flip the keys it leaves bare.

**Translation fixes** (`faithful(tree)`), each checked against BigQuery itself:

| BigQuery | DuckDB before | Now |
| --- | --- | --- |
| `NUMERIC` keeps 9 decimal digits | sqlglot writes `DECIMAL`, which DuckDB reads as `DECIMAL(18, 3)`: `CAST(0.0001 AS NUMERIC)` was 0 | `DECIMAL(38, 9)` |
| `EXTRACT(DAYOFWEEK)` is 1 for Sunday | 0 for Sunday | plus one |
| `EXTRACT(WEEK)` counts Sunday weeks (week 0 before the first Sunday) | ISO weeks: 2016-01-01 is 53 | `strftime(.., '%U')`, `WEEK(MONDAY)` is `%W` |
| `DATE_TRUNC(.., WEEK)` and `DATE_DIFF(.., WEEK)` start weeks on Sunday | sqlglot 26 writes Monday weeks | built from Monday weeks shifted a day |
| `SUBSTR(s, 0, n)` and a position before the start read from position 1 | `SUBSTR('abc', 0, 2)` is `'a'` | position 1 |
| `REGEXP_EXTRACT` without a match is `NULL` | `''` | `NULL` |
| `CONCAT`, `LEAST`, `GREATEST` are `NULL` when an argument is | sqlglot 26 writes DuckDB's, which skip NULLs | `NULL` |
| `CAST(NUMERIC AS STRING)` drops trailing zeros (`'1.5'`) | `'1.500000000'` | trailing zeros dropped |
| `DATE_TRUNC`, `DATE_ADD` on a date return a date | a midnight timestamp | read back as a date |
| a NULL array is returned as `[]`; structs compare by position | `NULL`; structs compare by field name | read that way |
| `a[OFFSET(i)]` and `a[ORDINAL(i)]` fail outside the array; `SAFE_OFFSET(-2)` is `NULL` | `NULL`; a negative index counts from the end | fails, or `NULL` for the `SAFE_` forms |
| `SAFE_DIVIDE` is `NULL` when the quotient overflows | `inf` | `NULL` |
| `EXTRACT(MILLISECOND/MICROSECOND ..)` is the fraction of the second only (999) | counts the whole seconds too (56999) | taken modulo 1000 or 1,000,000 |
| a backslash in a `LIKE` pattern escapes the next character; `LIKE ANY/ALL (..)` is one `LIKE` per pattern | no escape without `ESCAPE` | `ESCAPE '\'`, one `LIKE` per pattern |
| `SPLIT(s, NULL)` is `NULL` | the whole string | `NULL` |
| a set operation operand that is itself a set operation keeps its grouping | sqlglot writes no parentheses | parenthesised |

**Guards.** Where BigQuery fails, or where no faithful translation exists, the DuckDB run fails too, so the pair stays unknown instead of being refuted: integer products outside `INT64`; division, `MOD` and `DIV` by zero; `SUM` past `INT64`; a `FLOAT64` product, quotient, `POW` or `EXP` that overflows (DuckDB returns `inf`); `NUMERIC` products and quotients (BigQuery rounds them to 9 digits, DuckDB keeps 18 or switches to `DOUBLE`); `>>` of a negative number (a logical shift in BigQuery); `CAST(FLOAT64 AS STRING)` (`'2'` against `'2.0'`); strings cast to numbers, booleans, dates or timestamps in any form the engines may read differently (`'1.0'` or `'1e3'` as `INT64`, `'t'` as `BOOL`, `'nan'` and `'inf'`); `EXTRACT` from an interval (BigQuery keeps 36 hours as 36 hours, DuckDB as 1 day 12 hours); a result holding an interval, an array with a `NULL` element or a non-finite float. A whole query is refused when it uses `FORMAT`, `COLLATE`, approximate aggregates, `UNNEST .. WITH OFFSET` (sqlglot writes a 1-based `WITH ORDINALITY`), `BIGNUMERIC`, `WEEK(<weekday>)` other than Sunday or Monday, a `STRUCT` that is compared, grouped or read whole (an inline table `FROM UNNEST([STRUCT(1 AS a), STRUCT(2 AS a)])` runs when every row names its fields as the first row does, since DuckDB matches the rows by field name and BigQuery by position), a float literal large enough to overflow, JSON, `ARRAY_SLICE` (sqlglot keeps BigQuery's 0-based bounds), `PERCENTILE_CONT`/`PERCENTILE_DISC`, `CAST .. FORMAT` and `PARSE_DATE`/`PARSE_TIMESTAMP` (sqlglot drops the format, the zone or the `TIME` target), `AVG`, `STDDEV` and `VARIANCE` of a `NUMERIC` (exact in BigQuery, `DOUBLE` in DuckDB: a variance of values 1e-9 apart came back 0), a `CAST(TIMESTAMP AS STRING)` whose fractional seconds are not in groups of three digits, a time zone that is not a named zone (`'UTC+1234'`), `FORMAT_TIMESTAMP`/`DATETIME` in a time zone (sqlglot drops it), `LIKE ANY/ALL` over an array or subquery, `ROUND` with a rounding mode, `UNPIVOT` (DuckDB puts the name column first), `ROLLUP`/`CUBE`/`GROUPING SETS` keys that are not columns, `SELECT AS STRUCT/VALUE` read as a table, `GROUP BY ALL` without a grouping key, date or time text lined up with a date in a set operation, `ANY_VALUE(.. HAVING MAX/MIN ..)`, `REGEXP_INSTR` with an occurrence or return position, `IN` over a struct holding a `NULL`, a string escape sqlglot leaves undecoded (`\x41`, `\u20AC`, `\101`, `\?`) and a `BYTES` literal with a backslash, `CURRENT_DATE` and its kin in a time zone (sqlglot 26 drops the zone), and `ARRAY_AGG`, `STRING_AGG` or `ARRAY(subquery)` without `ORDER BY` (BigQuery picks the element order).

The guard macros bind each argument once. DuckDB pastes a macro's arguments in wherever its body names them, so a guard that read `a` five times made a division nested in another division five times larger per level: a variance written with divisions, products and sums took 0.15 s to plan on an empty table (20 times the plain query), and a division nested five deep took 12 s. Each macro now packs its arguments into one struct handed to a lambda, so a field is read where the body names it and has the argument's own type. Only `kumo_bq_read` keeps the plain form, because it tests `typeof(x) = 'VARCHAR'` and a bare `NULL` argument becomes a `VARCHAR` field. Before this, the targeted-data eval's per-query budget ran out on 6 of its queries that had finished before the guards.

As a result DuckDB never holds a NaN or an infinity during a BigQuery run, so the NaN rules (NaN equal to itself and above every number in DuckDB, unequal and first in BigQuery) cannot decide an answer.

A database on which a guard fires is one BigQuery fails on: the searches skip it and try the next one (`is_bigquery_failure(error)`), and `check_result_equivalence` does not count it. One consequence: a pair told apart only on a database with a zero divisor is no longer refuted there, since BigQuery shows an error on it, not a difference.

**Searches that report a difference.** Besides running BigQuery's reading, a reported difference must be one BigQuery would show:

- **Compare queries** (`POST /api/prove-queries`) runs a second search after the prover's own. It now keeps declared foreign keys and treats a key's columns as NOT NULL, checks the database it reports against every declared fact, runs the two pasted queries as written on it (the shrinking step may simplify the queries), and reports nothing for a query that may pick rows freely (`LIMIT` without `ORDER BY`, `ANY_VALUE`, `RAND`...) or whose output changes when the rows are stored in another order (ties broken by position).
- `check_result_equivalence` answers *inconclusive*, not *different*, when such a query is involved.
- The standalone search (`kumosql.counterexample`) and the bounded check's replay reverse and rotate every table before their random shuffles, so a difference that rests on which of two rows comes first is dropped (random shuffles alone kept a two-row table in order one time in eight). Shuffling cannot move a pick that follows DuckDB's hash order, so the standalone search also reruns a candidate with every `ANY_VALUE`, `first`, `last` and `arbitrary` call guarded (it fails unless the group holds one value, or only NULLs) and with every output column added to a top-level `LIMIT`'s `ORDER BY`, ascending and descending. A pair that picks as a window function, or inside an ordered call, stays unknown ([the checks](evals/verieql.md#counterexample-generator)).
- The bounded check reads a key's columns as NOT NULL, matches a foreign key only to a non-NULL parent value, and keeps `NUMERIC` values within BigQuery's range and 9 decimal digits (`BIGNUMERIC` within its own; replay loads `NUMERIC` as `DECIMAL(38, 9)`).

Not acted on: comparisons BigQuery rejects at compile time (`1 = TRUE`, `1 = '1.1'`, `ARRAY` equality or ordering, nested arrays). BigQuery has no result for such a query, so there is nothing for a DuckDB difference to contradict. `CAST(TIMESTAMP AS STRING)` with fractional seconds and decimal literals (exact in DuckDB, `FLOAT64` in BigQuery) are also left as they were; the second matches how the provers read literals.

The rows of Google's [GoogleSQL compliance tests](evals/googlesql-expected-results.md) check this layer from outside: each supported query's expected rows against what the translation returns. They found the milliseconds, `LIKE`, `SPLIT`, set-operation and most of the refusals above.

`tests/test_bigquery_on_duckdb.py` keeps one test per divergence, with the values BigQuery returned, and pairs that BigQuery finds equal but the searches used to refute. The divergence list started from an outside catalogue (35 rows) and was checked row by row in DuckDB 1.5.6 and BigQuery; the table above includes several divergences that catalogue missed. `tests/test_false_refutation_audit.py` keeps the 15 pairs of an outside audit of false refutations, each run through every search that could report it. 150 examples from BigQuery's documentation were also replayed through this layer: each one matches the documented output up to formatting, fails, or is refused. The exceptions are `CURRENT_DATE`, documented with a past date, and two where BigQuery itself disagrees with the page (`CHR(0)` is not `''`, and `EXTRACT(WEEK(MONDAY) FROM TIMESTAMP '2017-11-06 00:00:00+00')` is 45).
