# Local browser UI

[Plain-language version](../docs_simple/ui.md)

How the local browser UI works: starting it, its pages, saved state, scopes, data sources and tags.

## Local browser UI

Install into a virtual environment (see [Getting Started](getting-started.md#1-install) for macOS, Linux and Windows), then start the local editor:

```shell
python -m kumosql.ui
```

`python -m kumosql.ui` is the form that always works, including on locked-down Windows machines where the `kumosql-ui.exe` launcher that pip creates is blocked or its Scripts folder is not on `PATH` (pip warns about this at install time and it is harmless). `kumosql-ui` is the same program and can be used wherever launchers run. Files whose path is longer than Windows' 260-character limit are read through extended-length paths, so no administrator setting is needed. Every other command has a `python -m` form too, see [Command-line tools](../README.md#cli).

Open the URL printed by the command (`http://127.0.0.1:8765/`) if your browser does not open automatically. Turn on transformations in the **Pipeline** strip across the top, paste BigQuery SQL or Dataform SQLX (or open or drop a `.sql`/`.sqlx` file) into **Original SQL**, and review the highlighted result, a line diff, and the per-step verification report. Use **GitHub** (beside **Open**) to browse the SQLX models in a public Dataform repository and open a file in the editor. Rules run top to bottom; drag them or use the arrows to change the order. The result updates after a short pause while typing, or use **Transform SQL** or Ctrl+Enter. Output that cannot be verified remains visible with a review warning. **Examples** loads sample SQL for each rule, and the result can be copied, downloaded, or sent back to the editor for another pass.

The server listens only on `127.0.0.1` and uses the existing Python package. Pasted SQL stays local. Connecting a repository runs your local `git` (see below). GitHub browsing contacts GitHub only when you connect a repository or open one of its files; it supports public Dataform repositories and is read-only. The **BigQuery** page shows an **Explorer** tree in a left panel, like the BigQuery console: projects, then their datasets, tables and functions, then each table's columns (nested fields open too), each level read with your Google Cloud credentials when you open it. The body beside it is left empty for content to come. A ↻ on a project, dataset or table re-reads just that node, **+** at the top opens the project choice, and tick a table to tag it. Catalog answers (projects' datasets, tables and schemas) are saved in memory and in `catalog-cache.json` in the KumoSQL data directory, so they appear instantly and survive restarts. They are re-fetched only once older than the **query cache lifetime** in Settings under *BigQuery projects* (48 hours by default): an expired answer is still shown at once and refreshed in the background. Each tree node has a ↻ icon that re-reads just that level from BigQuery, for example right after you create a table, and the ↻ at the top of the Explorer re-reads everything open. The page shows how old the saved copy is, and keeps showing it if BigQuery is unreachable. Otherwise it contacts BigQuery only when you open that page or select an item you have not seen; the SQL editor itself remains local. Use `python -m kumosql.ui --no-browser` to start without opening a browser, or `--port 8766` to choose another local port. Stop it with Ctrl+C. No UI-specific dependency is required. **What the console shows.** On start it prints the KumoSQL version and commit, the Python path (flagging the Microsoft Store build), the git version, the local data folder, the settings file and the log file. While running it prints one line per background task (start-up repository reload, Dataform schedule lookup, BigQuery catalog refresh) with its duration, every git command with its folder, exit status and time (and `git fetch still running after 10s ... may be waiting for credentials` for a slow one), and each error as one clear line followed by the traceback when it is unexpected. Request lines (`GET /api/...`) are quiet by default and go only to `ui.log` in the KumoSQL data directory (rotated at 1 MB); `--verbose` also shows them in the console. Console output is written by its own thread and git gets no console input, and on Windows QuickEdit is switched off at start-up, so clicking in the console window cannot freeze the UI.

**Query graph**, **Cost** and **Change reports** show your own data and nothing else; there is no sample data. Until a project is loaded each page says what to load. Connect a project under **Settings → Repositories** (a Dataform git remote and optional branch; it is saved and reloaded every time KumoSQL starts, and the pages offer **Fetch latest**), by starting the server with `python -m kumosql.ui --git URL [--branch B] [--refresh]` or `python -m kumosql.ui --project DIR` (a Dataform or SQL folder), or by `POST`ing `{"files": {path: text}}` to `/api/project`. Add job history with **Load job history** (a BigQuery job-history export as JSON, JSON lines or CSV, such as `bq query --format=json` over `INFORMATION_SCHEMA.JOBS`, whose `referenced_tables` and `destination_table` use `project_id`, `dataset_id` and `table_id`; `POST /api/jobs` with `{"filename", "text"}`, or `python -m kumosql.ui --jobs FILE`). It stays loaded when you load another project and is saved in the KumoSQL data folder (`job-history/jobs.jsonl`), so it is still loaded after a restart; **Remove job history** drops it and deletes the saved copy. The **Query graph** has two views, chosen with the **Explorer / Simple** switch and remembered in the browser. **Explorer** (the default) is built for pipelines with thousands of assets: zoom and pan (the mouse wheel zooms about 2.5 times faster than Cytoscape's default), an automatic left-to-right layered layout, hover highlighting, a minimap, **Focus selection** (the selected asset with its upstream, downstream or both, 1 to 5 hops or all), and collapse by dataset (one dataset from the picker, or **Collapse all**; click a collapsed dataset to expand it). It draws with [Cytoscape.js](https://js.cytoscape.org/) (MIT), vendored in `static/vendor/` so nothing is fetched from the internet. The **Dataform tags** filter above the graph lists the `tags` found in the models' config blocks; tick one or more to keep only the assets carrying any of them (actions with no tags or `tags: []` simply have none). Both views have a **Full screen** button in the top-right corner of the graph (Esc exits) that fills the screen with the graph. **Simple** is the original fixed layout of every asset, best for small projects; `python tools/make_large_project.py DIR --nodes 2500` writes a synthetic project to try Explorer on. It shows every gap the analysis found and a "Partial graph" strip whenever any asset could not be analyzed; job history adds observed edges. **Cost** lists where the same work repeats in your models and, with job history, the measured cost per asset, the share that cannot be attributed to an asset (with the reason), and the cost rule catalog. Values are bytes billed until you enter a price per TiB (kept in this browser only; `GET /api/cost?rate=`). It claims no saving: that needs a proposed change. **Change reports** compare the loaded project, when it came from git, against another branch of the same repository (**Compare**, `POST /api/changes/compare` with `{"base": "main"}`), and show behavior, cost basis, consumers, already-done-elsewhere matches, evidence coverage and the code review check for that comparison. Guided refactors and query sources come from the loaded project. The comparison is kept in memory only; project metadata is also saved as a JSON snapshot. [docs/ui-roadmap.md](ui-roadmap.md) lists the data shape behind each area.

**Shared models** lists the CTEs copied into several models of the loaded project and writes the patch that moves one into a new model, with a prover result for every model it touches; see [Shared models](shared-models.md).

**Large projects load in two steps.** The graph appears as soon as the models are parsed. The slow searches for identical and similar queries (used by Cost and Change reports) run in the background, and those pages show "Analyzing your models" with progress until they finish. Loading the same content again, such as the same commit, reuses the finished analysis. The console and `ui.log` get one timing line per stage, for example `analyse: 3.87s (models 2500)`; set `KUMOSQL_TIMING=0` to silence those console lines. The rest of the app stays usable while this runs: the server is threaded and uses a short interpreter switch interval, so Settings, the BigQuery tab and page changes stay responsive (under about 0.2 s measured during a 5,000-model build), and the sidebar shows what is running (`GET /api/status`). Finished repeated-work and shared-logic results are also saved by content (commit) in the `analysis-cache` folder of the KumoSQL data folder, so reloading the same commit after a restart skips those searches. In Python, `Pipeline.report(include_duplicates=False)` skips the duplicate searches. Long stages print a `started` line, a "still running" line with progress every five seconds (for example `analyse > trace columns: still running after 84s, 407/2400`), any model slower than three seconds, and the slowest few at the end; models appear as redacted placeholders (`model#417`), never by real name, so a log is safe to share. Column tracing asks sqlglot not to copy a model's whole query once per output column (that copy made wide, CTE-heavy models take seconds each; they now take tens of milliseconds), and garbage collection is tuned while a project is analysed. As a safety net to keep a load bounded, a model whose column tracing exceeds 60 seconds, or all tracing after 600 seconds in total, is traced at table level instead: its reads, readers and column names stay in the graph and each of its columns is treated as depending on everything the model reads (so impact and dead-column answers stay safe but coarser). It is listed as a `lineage_skipped` gap, never as an error, and the graph shows "Partial graph". Change the limits under **Settings → Analysis** (`0` for none), or with `KUMOSQL_LINEAGE_MODEL_SECONDS` and `KUMOSQL_LINEAGE_SECONDS`, which override Settings; a saved analysis is only reused under the same limits. `python tools/make_large_project.py DIR --messy` adds awkward files (wide tables, unions, JS blocks, operations, missing refs, cycles, syntax errors).

To use the catalog with Google Cloud CLI credentials, install the BigQuery extra and sign in with Application Default Credentials:

```shell
python -m pip install '.[bigquery]'
gcloud auth application-default login
```

The browser uses the active ADC identity and read-only BigQuery scope. The tab starts empty: choose the projects you care about under *BigQuery projects* in Settings (the **+** at the top of the BigQuery Explorer opens it), either by typing a project ID or by browsing the projects your identity holds a role on, which is only fetched when you ask. The choice is saved with your other settings, only chosen projects are listed, and a project is refused if BigQuery denies you access to it, so nothing loads for projects you have not picked. *BigQuery projects* in Settings also holds a **billing project**, the project that queries KumoSQL runs and bills in (checked with a free dry run; features that run queries say a billing project is needed until it is set), and a **query cache lifetime** in hours (default 48) for reusing results of those queries. Both are read from `GET /api/catalog/settings`, or in Python `bigquery_catalog.billing_project()`, `require_billing_project()` and `query_cache_seconds()`. Datasets get the same treatment with a one-row table listing, and hidden anonymous datasets whose names start with an underscore (cached query results) are never shown, as in the BigQuery console. A table that turns out to be inaccessible when opened (403 or 404) is removed from the list and the saved copy. The probe is a free metadata call and the result is cached like the rest of the catalog; BigQuery permissions still control which datasets, tables, and schemas appear. `gcloud auth login` alone does not configure Application Default Credentials.

**Saved state.** UI preferences (theme, enabled rules and their order), named SQLFluff formatting configurations, and scopes are saved by the local server in one JSON file in the standard per-user data directory (`%APPDATA%\kumosql\state.json` on Windows, `~/Library/Application Support/kumosql/state.json` on macOS, `$XDG_DATA_HOME/kumosql/state.json` or `~/.local/share/kumosql/state.json` on Linux). Set `KUMOSQL_HOME` to use another directory. The CLI and Python API read the same file, so a scope saved in the UI works with `--scope`.

**Project file trust and caches.** Uploaded and Git project paths must be relative in both POSIX and Windows syntax: drive prefixes, colons (including alternate data streams), rooted paths, reserved device names, trailing dots/spaces in path parts and traversal are refused (an upload fails with a clear error; a Git repository file with such a name is skipped, since it could not be checked out on Windows either). Writes also check that the resolved target stays inside the temporary checkout. Local project loading skips file and directory symlinks and Windows directory junctions, including linked settings files, and records a completeness gap for skipped assets/settings. Parsed project snapshots in `parse-cache/` are versioned, validated JSON model metadata and source text. Restart loading skips Git and SQLX parsing but rebuilds SQL analysis and lineage from that metadata. Missing, damaged, stale or invalid snapshots are cache misses. Legacy pickle snapshots are never read; reload a project once to create its JSON snapshot. Analysis results continue to use JSON in `analysis-cache/`.

**Formatting and complexity.** The `format_sql` operation formats BigQuery SQL with [sqlfluff](https://sqlfluff.com) and is verified like every other rule. Open *Settings* from the bottom of the sidebar (or press Ctrl/⌘ + , or click the *SQL formatting* link under the pipeline) to set keyword case, comma position, indentation, line length, and which sqlfluff rules to apply. The *Rules* list shows every BigQuery rule in the installed sqlfluff, grouped by category with its description, each with an on/off switch; rules sqlfluff can only lint, not fix, are marked and stay off because they can't change formatted SQL. Settings opens as a panel over the current page and saves changes as you make them, except renaming a configuration, which waits for the *Rename* button. Save multiple named configurations and switch between them; the pipeline shows which one is active, and it is included in the server's persistent local state. The stats bar shows a structural complexity score before and after (hover for the breakdown). The score is a weighted sum of joins, CTEs, subqueries, set operations, `CASE` expressions, window functions, `AND`/`OR` predicates and SELECT nesting depth, banded low (<10), moderate (<25), high (<50) or very high. sqlfluff cannot parse Dataform SQLX, so those inputs are left unformatted and unscored. The same is available in Python: `format_sql(sql)` and `complexity(sql)`.

**Scopes.** A scope is a saved, named *rule* that decides which records are "in": models, job-history rows or table profiles. A rule combines conditions on any field with AND, OR and NOT groups that nest, for example `job submitter IN [ana@co.com, bo@co.com]`, or `dataset starts with raw AND NOT project = sandbox`. Build one in *Settings → Scopes* (open Settings from any page, or use the *Manage* link under the Pipeline strip; the rule builder suggests the fields found in the loaded project and job history, and accepts any field name) or from the shell:

```shell
python -m kumosql scopes add "My Team" --rule '{"field": "submitter", "op": "in", "value": ["ana@co.com", "bo@co.com"]}'
python -m kumosql scopes add "Raw, not sandbox" --rule-file rule.json
python -m kumosql scopes add "My Projects" --field project growth-*      # simple "field in values" shortcut
python -m kumosql scopes fields --root path/to/dataform --observed-reads jobs.json   # fields a rule can use
python -m kumosql scopes list
python -m kumosql pipeline-report path/to/dataform --scope "My Projects"
```

A rule is JSON: a condition is `{"field", "op", "value"}`; groups are `{"all": [...]}` (AND), `{"any": [...]}` (OR) and `{"not": rule}`. Operators: `eq`, `ne`, `in`, `not_in`, `prefix`, `suffix`, `contains`, `glob` (`*`, `?`), `regex` (a search), `gt`, `gte`, `lt`, `lte` (numbers, ISO timestamps, else text), `is_null` and `not_null`. Text comparison is case-insensitive unless a condition sets `"case_sensitive": true`; a list-valued field (a table's `columns`) matches when any element does; `labels.team` reads inside a nested object.

**Jobs run by a team.** To scope to jobs run by your team, add a condition on `user_email` with *is one of* and paste the addresses (one per line, or separated by commas or semicolons; case does not matter). `user_email` is the column of BigQuery's `INFORMATION_SCHEMA.JOBS`, and any job-history row that carries it works, so no other setup is needed; combine it with more conditions (for example `job_type` equals `QUERY`) using the builder. The other `INFORMATION_SCHEMA.JOBS` columns (`project_id`, `job_type`, `statement_type`, `total_bytes_billed` and so on) are suggested in the field list even before job history is loaded. From the shell: `python -m kumosql scopes add "My team" --rule '{"field": "user_email", "op": "in", "value": ["ana@co.com", "bo@co.com"]}'`. The rule applies when job history is loaded; without it the page says that the field is not available.

**What a scope applies to.** Each saved scope has an `applies_to` list of data domains: `models` (Dataform models), `jobs` (job history) and `bigquery` (BigQuery tables, where tag rules use scopes). In Settings → Scopes a scope is one card: its rule, then the domains it applies to; one scope is one concept across every source. Pages honor a scope only for the domains it lists (a scope that applies to `models` alone leaves job history unfiltered), and a tag rule refuses a scope that does not list `bigquery`. Scopes saved before the list existed are migrated to the domains their fields can be evaluated on. From the shell: `python -m kumosql scopes add "My team" --rule-file rule.json --applies-to models jobs`.

**Data sources.** Settings → Data sources holds saved queries whose rows scopes and tag rules can use. *New data source* asks for a name, the source type (BigQuery SQL is the only one so far), the query (for example `SELECT * FROM project.dataset.INTERNAL_METADATA_TABLE`) and the cache lifetime in hours, which starts at the global query cache lifetime from Settings → BigQuery projects. *Close* discards, *Save* keeps the source, and *Save and Populate* also runs the query. The query runs in the billing project from Settings under the byte cap of Settings → Scopes (a dry run first, then `maximumBytesBilled`); the rows are kept in the data folder (`data-sources/<id>.json`) and reused until the lifetime ends, or until the query is edited. If a re-run fails the older rows stay and are marked stale. Each saved source is an *Applies to* choice of scopes (`source:<id>` in `applies_to`), and its columns are rule fields in the scope and tag rule builders, like `user_email` for job history. A scope whose fields all come from one source is saved as applying to it. A source with a `full_name` column (`project.dataset.name`) is joined to BigQuery objects and to Dataform models (by each model's target table), so its other columns work as fields in tag rules and in scopes: a scope on those columns that applies to Dataform models filters the graph, cost and changes pages (a field with several matching rows matches when any of them does). A scope that applies only to a source, not to models, leaves those pages unfiltered. Deleting a source removes its rows and its place in scopes' `applies_to`; a scope that would be left applying to nothing blocks the deletion.

**Scopes built from scopes.** A rule can include another saved scope (`{"scope": "my_team"}`; *+ Scope* in the builder), so `our_department` can be defined from `my_team` and `partner_team`. Use OR (`{"any": [...]}`) for the union, everything in either team, which is what a department normally means; AND (`{"all": [...]}`) gives only what both scopes contain, and `{"not": {"scope": ...}}` excludes one. References nest, and a scope cannot refer to itself directly or through others: saving such a scope is refused, naming the chain. A reference to a scope that is not saved is refused too, and a scope that other scopes use cannot be deleted until they stop using it. Edits to `my_team` apply to `our_department` the next time it is used.

**Values from a SQL query.** A condition can use *is returned by SQL query* (`{"field": "user_email", "op": "in_query", "query": "SELECT user_email FROM `proj.hr.my_team`", "column": "user_email"}`): the field must equal one of the values the query returns, so a team kept in a BigQuery table stays current without pasting addresses. `column` is optional (the first column is used). Guardrails:
- The query runs in the billing project chosen in Settings → BigQuery projects; without one the condition reports that a billing project is needed.
- It is dry-run first and refused when the estimate exceeds the cap; BigQuery is also told to bill no more than the cap (`maximumBytesBilled`). The cap is set in Settings → Scopes (default 1 GiB); the query is labeled `kumosql=scope_query` and returns at most 200,000 values.
- The result is kept for the cache lifetime set in Settings → BigQuery projects (default 48 hours), in memory and in `scope-query-cache.json` in the data directory, so reopening a scope does not bill again. After the timer the query re-runs when next needed; if that fails the old values are used and flagged. *Check (free)* dry-runs only, *Run and keep* runs it, and *Refresh now* bypasses the timer; the last run time is shown.
- From the shell: `python -m kumosql scopes refresh [NAME] [--check]` runs (or only dry-runs) the query conditions. HTTP: `GET/POST /api/scope-queries` (`mode`: `status`, `check`, `run`, `refresh`) and `PUT /api/settings/scope_queries` for the cap.

Fields are discovered, not hardcoded. Models have `project`, `dataset`, `table`, `name`, `model`, `kind`, `path`, `depends_on` and `tag` (the object's [tags](#tags)); table profiles add `grain_status`, `grain_keys`, `columns`, `column_count`, `profile_complete` and `row_filters` (computed only when a rule uses one); job-history rows have `job_id`, `creation_time`, `destination`, `referenced_tables` plus whatever else each row carries (a submitter, labels, bytes billed). A field the data does not have is an error that names it and suggests the closest match ("did you mean `dataset`?"), never a scope that silently matches nothing: for example a `submitter` rule used on the pipeline report is rejected, and a typo in a job-history rule is rejected when the graph is built. A record that merely lacks a known field counts as empty for it.

Scopes saved by earlier versions (`field in values`, with a trailing `*` as a prefix match) are migrated to rules the first time they are read: one condition per field, joined with AND. Rules live in the `scopes` section of `state.json`. In Python, `Scope.matches(record)` and `Scope.filter(records)` apply a scope to any dicts, `Scope(name, rule=...)` builds one, and `discover_fields(pipeline, observed_reads, profiles)` lists the usable fields. `Pipeline.report(scope=...)`, `assess_change`, `find_overlaps`, `find_rollups` and coverage limit results to the models the rule matches, and `observed_scope` applies it to job history in the graph. A scope that matches no models prints a warning.

**Choosing the active scope.** The Query graph, Cost and Change reports pages have a *Scope* picker at the top. The choice is remembered in the browser and sent to the server as `?scope=NAME` on `/api/graph`, `/api/impact`, `/api/overlaps`, `/api/cost` and `/api/changes`. With a loaded project, a rule on model fields limits the models and lineage, a rule on job-history fields (such as a submitter) limits the observed reads, and the page says which it did: a rule on job fields shows "Applied to job history only: models have no ...". A rule that no data source can evaluate is an error naming the field. With no project loaded there is nothing to filter, and the page says so. Duplicate groups are kept when any occurrence is in scope, so they can list out-of-scope occurrences as context.

## Tags

Tags are labels on anything that lives inside a dataset: tables, views, materialized views, functions (UDFs), table and aggregate functions, procedures, and Dataform models and declarations. They are **KumoSQL's own metadata**, saved in the `tags` and `tag_rules` sections of the same local settings file as scopes, and are never written back to BigQuery as labels, so your real projects do not change. An object is named `project.dataset.name`; matching ignores case.

- **By hand.** On the BigQuery tab, each table, view, function and procedure has a checkbox: tick several (or *Select all*) and add or remove a tag on all of them at once, or open one to edit its tags next to its schema. On the Query graph, selecting a node shows a *Tags* editor, and the simple view shows tags on each box. Functions and procedures are listed after tables (a second metadata call per dataset; if BigQuery refuses it the tables still show) and have no schema to read.
- **By rule (batch).** *Settings, Tag rules* holds rules of the form "objects matching *conditions* get tag *X*". The conditions are the scope rule builder: nested AND/OR/NOT, *is one of* with a pasted list, patterns, and other saved scopes. Fields: `project`, `dataset` (also `schema`), `name`, `type` (`TABLE`, `VIEW`, `MATERIALIZED_VIEW`, `EXTERNAL`, `UDF`, `TABLE_FUNCTION`, `AGGREGATE_FUNCTION`, `PROCEDURE`, or the Dataform kind for objects only in a repository), `kind`, `path`, `full_name`, `source` (`bigquery`, `dataform`). For example, `dataset equals RETIRED` gets `Retired`, so every table, view, function and procedure in that dataset is tagged. *Preview matches* shows how many objects a rule would tag before you save it. `full_name` is `project.dataset.name`. A rule can use *is returned by SQL query* (for example `full_name` is returned by a query listing the tables you retired), run in the billing project with the same bytes cap and cache lifetime as scope queries, so a rule is re-evaluated from the cache until it expires; if the query fails (no billing project, over the cap) that rule shows its error and tags nothing. A rule cannot use the field `tag`, since that is what rules produce; saving one is refused.
- **Always current.** Rules are evaluated when tags are read, over the Dataform project loaded now and the saved BigQuery catalog (never a live BigQuery call); the catalog of every project chosen under *Settings, BigQuery projects* is listed in the background when tags are first read (datasets, then each dataset's tables and routines: free metadata calls, no query, saved with the same cache lifetime), so a rule such as `dataset equals ARCHIVE` tags every matching table, view and function in those projects even if you never expanded them. While that runs, `/api/tags` says `syncing` and the pages ask again every few seconds. A project or dataset that cannot be listed (no credentials, no access) is reported under `sync_errors` and retried after a few minutes. Projects you did not choose are never listed, so a reloaded repository or refreshed catalog is tagged again with no extra step. Tags from a rule show as dashed chips and cannot be removed by hand; hand tags show as solid chips and survive rule changes. A Dataform model that names its dataset but not its project joins the one BigQuery object it matches; an ambiguous name stays separate.
- **Using tags.** Filter the BigQuery tab's list or the Query graph (*Tag* picker, or `/graph?tag=Retired`) by tag. `tag` is also a scope field, so a scope can say `tag is one of Retired, Deprecated` and limit graph, cost and change pages to it.

HTTP: `GET /api/tags` (tags per object, tags in use, and how many objects each rule matched), `PUT /api/tags` (`{"keys": [...], "add": [...], "remove": [...]}`), `PUT /api/settings/tag_rules` (a list of `{"tag", "rule"}`), `POST /api/tag-rules/preview`. In Python: `kumosql.tags.snapshot()`, `change_manual()`, `save_rules()`, and `Pipeline.model_record(...)["tag"]`. Writing tags to BigQuery as labels is not done; it could be added later as an explicit option.

### Catalogs

**Catalogs.** A catalog is a saved, named rule for what a team *owns*: tables, views, functions (UDFs) and procedures, including BigQuery objects written outside Dataform (a workbook's output tables, say). It is the same rule builder as scopes and tag rules (nested AND/OR/NOT, *is one of*, saved scopes, *is returned by SQL query*, data-source columns joined by `full_name`) over the Dataform project loaded now and the saved BigQuery catalog; a catalog rule may also use `tag`, but not `catalog`. Build them in *Settings → Catalogs*, which shows how many objects each one owns and lets you preview a rule before saving. The built-in **Dataform repository** catalog (every model of the loaded repository, not its declarations) is active by default, so nothing changes until you add a catalog and make it active; several catalogs can be active at once (their union). The active catalogs decide what counts as "ours": graph nodes outside them are drawn dimmer (`owned` per node, `catalogs` in `/api/graph`), the impact of a change still lists every reader but marks those outside as *Other owner* (`owned` per reader, `not_owned` and `catalogs` in `/api/impact`), the Changes page marks changed models outside them as *Other owner* (`owned` per change in the report), and the Cost page considers only models they own. Every object also has a list field `catalog`, so a scope or any other rule can say `catalog is one of My team`. Catalogs are saved in the `catalogs` section of `state.json` (the active ones in `catalogs_active`). In Python: `kumosql.catalogs.members(names)` returns the normalized `project.dataset.name` of every owned object, and `Pipeline.assess_change(..., owned=catalogs.owned(pipeline))` flags readers. HTTP: `GET /api/catalogs`, `PUT /api/settings/catalogs` (the list of `{name, rule}`), `POST /api/catalogs/active` (`{"active": [names]}`) and `POST /api/catalogs/preview`.
