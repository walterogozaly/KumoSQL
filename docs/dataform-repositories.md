# Connecting Dataform repositories

Connecting private Dataform repositories, the local data folder, logging and diagnostics, and production schedules.

## Connecting a private Dataform repository

The query graph loads a repository through the local `git` CLI, so private repositories work with the credentials you already use (SSH keys, a credential helper, or a token in an `https://` URL). KumoSQL never asks for or stores credentials and makes no unauthenticated HTTP requests for this.

```bash
python -m kumosql.ui --git git@github.com:owner/dataform-project.git --branch main
python -m kumosql pipeline-report --git https://github.com/owner/dataform-project.git --refresh
```

**Local data folder holds everything.** Once you choose the folder (Settings → Local data folder), all of KumoSQL's files live there: `state.json` (formatting and SQLFluff-style rules, saved scopes, BigQuery project selection and billing project, connected repositories, UI preferences), the caches (`catalog-cache.json`, `scope-query-cache.json`), `ui.log`, and `git-cache`. Only a tiny pointer file, `location.json` in the default per-user location (`%APPDATA%\kumosql` on Windows, `~/.local/share/kumosql` on Linux, `~/Library/Application Support/kumosql` on macOS, or `$KUMOSQL_HOME`), records where the folder is. When you first choose or later change the folder, the existing files are moved into it and the dialog lists what moved; a file that already exists in the new folder is kept and the old copy is left in place, and nothing is deleted. Clones in `git-cache` are not moved (they are fetched again on their next load). A folder chosen with an earlier version is moved over automatically. Code that stores something new uses `kumosql.state.data_path("name", ...)`, which returns a path inside the data folder (creating its parent directories), so new stores follow the setting too; `state.data_dir()` is the folder itself. `GET /api/storage` reports `folder`, `pointer` and `files`. Accepted remotes are `https://`, `ssh://`, `git@host:path` and local repository paths. The repository is shallow-cloned (depth 1) into `git-cache` inside your **local data folder** (**Settings → Local data folder**, `GET`/`POST /api/storage`; `KUMOSQL_GIT_CACHE` overrides it). Connecting a repository in Settings requires that folder to be chosen first, because the default location can fail: the Microsoft Store build of Python hides writes under AppData from `git.exe`. Saving the folder checks that it exists, is writable, and that git can read a file Python wrote there; pick one in your home folder (suggested: `KumoSQL` there). Changing it later does not move existing clones: repositories are cloned again on their next load and the old folder can be deleted. Before a folder is chosen, `--git` and `pipeline-report --git` still use a default (home folder on Windows, the KumoSQL data directory elsewhere) and reused on later runs; `--refresh` (or **Fetch latest** in the UI) fetches the newest commit of the branch. Git never prompts: when authentication fails you get git's own message, for example `Permission denied (publickey)`, followed by a reminder to sign in to git on this computer (Git Credential Manager, an SSH key, or the GitHub CLI: `gh auth login` followed by `gh auth setup-git`, which is what lets git itself use that login for https URLs; `gh auth login` alone does not). `git` always runs from an existing directory, never the server's own. KumoSQL uses the URL you enter and never turns an https URL into SSH; it also refuses to load when your git configuration (`url.<base>.insteadOf`) would change the protocol. The one conversion goes the other way, as a fallback: when an SSH remote (`git@host:owner/repo` or `ssh://...`) fails to connect (no `ssh` program, port 22 blocked, no key, host key refused), KumoSQL retries the equivalent `https://host/owner/repo` URL, says so (the repository's entry in Settings shows "Loaded over https ... because SSH did not work"), and remembers it so this computer goes straight to https from then on (the `git_transport` section of the settings file; delete the entry to try SSH again). If both fail, the error shows git's message for each and the exact remote URLs. A cached clone whose `origin` differs from the saved URL is pointed back at it before each load. If SSH is blocked on your network (port 22) and https fails too, the error says so.

**Logging and diagnostics (safe to paste).** One module, `kumosql.console`, writes everything the console shows and everything in `ui.log`: start-up, git, BigQuery, Dataform schedules, the analysis stages, requests and errors. Every line passes through `kumosql.redact` first, which replaces repository URLs and names, branches, GCP projects, datasets, tables, model names, file paths (the folder depth and file extension are kept), e-mail addresses, host names, secrets, the home folder and the user name with stable placeholders: `repo#1`, `project#2`, `dataset#3`, `model#417`, `dir/dir/file#88.sqlx`, `user~`. The same name always gets the same placeholder within a session, so a log can still be followed. Messages name the step and the outcome, not the thing: `repo load > sync cached clone > write cached clone: failed (PermissionError) after 0.1s [repo repo#1]: ... 'dir/dir/file#12.sqlx'`. Each stage logs its start and end with the time taken and counts, a "still running after 15s" line every 5 seconds on a long stage (with progress when known), and a warning when a git call is slower than expected. Each error is one line with a short code, for example `ERROR [KS-GIT-AUTH] ...`, followed by a `hint:` line that uses the `python -m kumosql.ui ...` form; the full traceback (file names and line numbers kept, messages redacted) goes to `ui.log` only. The real names behind the placeholders are saved in `redaction-map.json` in the local data folder (the last five sessions; it stays on that computer and is never part of any report). To look a placeholder up, run `python -m kumosql.ui --lookup model#417`. **Settings → Diagnostics → Copy diagnostics** (`GET /api/diagnostics`) copies a report with the KumoSQL, Python, git and OS versions, the kind of Python (Microsoft Store, virtualenv, conda or system), the settings with every name replaced, secrets hidden and SQL left out, the server status and the last 300 log lines; it is scrubbed even when redaction is off. Start with `python -m kumosql.ui --no-redact` (or set `KUMOSQL_NO_REDACT=1`) for local debugging only: logs then hold real names, and the report leaves the log out. For code: `console.say`, `console.warn`, `console.error(message, exc, code=..., hint=...)`, `with console.task("stage name", repo=url) as t: t.note(files=12); t.progress(done, total)`, `console.ref(kind, name)` for a placeholder in a message and `console.register(kind, names)` to tell the redactor about names before they are logged (kinds: repo, branch, project, dataset, table, model, file, email, host, name). `--diagnose-repo` output is redacted too. Redaction is pattern based plus every name KumoSQL has seen; SQL parse errors keep only the message and `Line N, Col: M`, never the SQL excerpt. A name that appears only in text KumoSQL has never parsed can still slip through, so skim a log before sending it.

If a repository will not load, `kumosql-ui --diagnose-repo URL [--branch B]` loads it once and prints the KumoSQL, Python, git and OS versions, the working, cache, temporary and state directories, every git command with the directory it ran in and its exit status, and the full traceback; paste that into a bug report. Always run it as `python -m kumosql.ui --diagnose-repo URL` (the Microsoft Store build of Python keeps its launcher scripts off `PATH`); the report warns when it detects the Store build. The running version and commit are shown at the bottom of the sidebar, at `GET /api/version`, and by `python -m kumosql.ui --version`, so you can tell whether an update took. Nothing in the UI waits for git: the start-up reload runs in the background (Settings shows "Loading with git…" until it finishes, and `GET /api/repositories` marks the entry `loading`), the saved list and Settings answer immediately while a load runs, and every git command gets no console input (`stdin` closed, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, no askpass program) and a 180-second limit, so a credential prompt fails with git's message instead of hanging. If something unexpected fails while the graph is built from the fetched files, the message names the repository and the step (the repository itself was fetched fine) and the traceback is in `ui.log`. A single file the analysis cannot handle is skipped and listed as a diagnostic that names the file (`asset_unreadable`), not a failure of the whole project. A Dataform `config` with `tags: []`, an empty config or no config at all loads normally. A byte-order mark at the start of a file (common on files saved on Windows) is ignored, a file in an older code page (such as Windows-1252) is read rather than dropped, `//` comments in `js` and `config` blocks may contain apostrophes and braces, and an assertion with no `schema` lives in the project's assertion dataset (`defaultAssertionDataset` or `assertionSchema`, else Dataform's default `dataform_assertions`). Loads are serialised, so a double click or the startup reload plus a manual one cannot corrupt the cached clone. A blank branch means the remote's default branch. If a refresh fails, the cached copy is kept. Only `.sqlx`, `.sql`, `.js` (the `declare()` and `publish()` calls refs resolve against; `node_modules` is skipped) and Dataform config files are read, straight from git objects: the clone has no working tree, so very long file paths (Windows' 260-character limit) cannot break a load.

**Settings → Repositories** keeps the list of connected repositories (saved in the `repositories` section of the local state file, with each one's last load time and last error). You can connect several; the active one feeds the Query graph, Cost and Change reports pages (cross-repository graphs are not built). When `python -m kumosql.ui` starts without `--project` or `--git`, it first shows the project it parsed last time straight from the data folder (`parse-cache`, one saved parse per commit, the last three kept; no git and no parsing, so a large repository is back in seconds), then reloads the active repository in the background, asking git for the latest commit and falling back to the cached copy (and saying why) if the remote is unreachable. When the latest commit is the one already shown, the saved parse is reused and nothing is parsed again; when the commit moved, the changed project is parsed once and saved. The saved parse is tied to the KumoSQL and sqlglot versions, so an update parses once more. **Refresh** in Settings, or **Fetch latest** on a page, pulls the newest commit on demand. The same list is available at `GET /api/repositories` and `POST /api/repositories` (replaces the list), `POST /api/repositories/activate` and `POST /api/repositories/refresh` with `{"id": ...}`. **Clear all repositories** (below the list, after a confirmation; `POST /api/repositories/clear`) removes every saved entry and the active choice, deletes the cached clones in `git-cache`, the saved Dataform schedule lookups, the saved analyses and parses and the remembered https fallbacks, and empties the loaded project, so the pages show "connect a repository" again. Your other settings, the local data folder and loaded job history are kept.

## Production schedules (Dataform workflow configurations)

When a repository is connected, KumoSQL looks up the Dataform repository whose git remote matches it and loads that repository's **workflow configurations** from the Dataform API, so the graph can show which models run on a production schedule. A configuration is *active in production* when it has a cron schedule, is not disabled, and uses the release configuration named `production`. A model counts as scheduled when an active configuration selects it by tag (`tags` in its `config` block) or by name, or reaches it through the configuration's include-dependencies / include-dependents flags; a configuration that selects nothing runs everything.

- **Credentials.** The same Google credentials as the BigQuery pages (`gcloud auth application-default login`, a service account, or `BQ_ACCESS_TOKEN`), asked for the `cloud-platform` scope Dataform needs. No extra token to paste. The credentials need to read Dataform repositories and workflow configurations in the projects searched.
- **Where it looks.** The projects chosen under **Settings → BigQuery projects**, in the default location `us-central1`. Each repository entry under **Settings → Repositories** has a *Production schedules* line with fields to override the projects and location for that repository (an empty field clears the override), plus **Refresh schedules**. Matching ignores case, a trailing `.git` or `/`, a `user@`, and the difference between `https://github.com/org/repo` and `git@github.com:org/repo.git`.
- **When it loads and refreshes.** After each repository load, in the background. The answer is saved with the catalog cache and lives for the **query cache lifetime** (48 hours by default); an older copy is shown at once and refreshed behind it, and **Refresh schedules** re-reads it now. If Dataform cannot be reached the saved copy stays, marked as such. If no Dataform repository has the remote, or Dataform returns an error, the entry says so; the repository still loads.
- **On the graph.** Scheduled models get a green edge in both views and a *Runs in production* tag in the detail panel that lists the schedules. `GET /api/graph` adds `schedules` to those nodes and a `workflow` summary.
- **Export.** `kumosql-workflow-configs https://github.com/org/repo --project my-project --location us-central1 --csv schedules.csv` (or `python -m kumosql workflow-configs ...`) prints or writes one row per configuration with the columns `REPO`, `WORKFLOW_CONFIGURATION`, `TAGS`, `SPECIFIC_ACTIONS`, `INCLUDE_DEPENDENCIES`, `INCLUDE_DEPENDENTS`, `CRON_SCHEDULE`, `TIME_ZONE`, `DISABLED`, `RELEASE_CONFIGURATION`, `ACTIVE_PRODUCTION`, `UPDATED_TS`. The API is `GET /api/workflow-configs`, `POST /api/workflow-configs/refresh` and `POST /api/workflow-configs/settings` with `{"id": ...}`.

## Declarations and refs

A `ref("name")` is resolved from what the project declares, never from the default schema alone. KumoSQL reads:

- `.sqlx` files with `type: "declaration"` (their own `database`, `schema` and `name`, else the project defaults);
- `declare({...})` and `publish("name", {...})` calls in any `.js` file, including `includes/`, when the name, schema and database are string literals, constants, or a loop variable over a literal list (`["a", "b"].forEach(...)`, `for (const t of [...])`). A list kept in another file is followed through `require("includes/sources")` or a relative path, with `module.exports = {...}`, `module.exports = [...]` or `exports.name = [...]`, including lists of `{database, schema, name}` objects (`SOURCES.forEach((s) => declare({schema: s.schema, name: s.name}))`); a member an item leaves out takes the project default. A list that is computed (`buildSources()`, `.map(...)`) is not followed.

Where it cannot decide, it leaves the ref unresolved (a `unsupported_ref` diagnostic, the dependency unknown) instead of guessing:

- a name declared in more than one schema (Dataform itself refuses to compile it);
- any ref to an unlisted name while a `.js` file declares tables it cannot read without running the code (`js_declaration_dynamic`). For exact results on such projects, load the compiled graph from the Dataform API.

When Google credentials allow and the repository is also a Dataform repository (found the same way as workflow configurations), KumoSQL reads the newest release compilation (else the newest compilation) from the Dataform API and takes every compiled action and declaration from it, so computed declarations resolve too. It is only asked when a `.js` file could not be read; the compilation may differ from the checked-out commit. Without credentials, or when no repository matches, refs stay unresolved (`compiled_graph_unavailable`); the parse is still saved, so a restart shows the project at once, but the load that follows parses it again instead of reusing it, so a later load with credentials tries again.

A table name that carries a dataset (`raw.orders`, `ref("raw", "orders")`) is matched on that dataset, never on its table name alone, so a staging model that shares its source table's name still reads the source. A bare `ref("orders")` that two actions answer to is ambiguous to Dataform itself and stays unresolved; spell the dataset (`ref("raw", "orders")`) to settle it.
