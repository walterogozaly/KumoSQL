# Additional public SQL sources for KumoSQL

Research date: **October 2, 2026**, America/New_York.

This is the research input as written. What KumoSQL already scores, and what is being added from it, is in the [inventory](evals/public-sources.md#additional-sources).

This second search adds discoveries beyond [the first source inventory](public-sql-evaluation-sources.md). It is intended as a handoff for selecting more evaluation material: new released artifacts, complete relational databases, actual SQL before/afters, and native GoogleSQL or SQLX workloads. Previously cataloged sources are excluded except where a newly identified artifact adds a materially different capability; those extensions are identified explicitly.

The strongest new additions are **SQLFluff structural rewrite fixtures, Trino paired query tests, reproducible engine bug witnesses, Mozilla BigQuery tests, Arcwise SQL corrections, Oracle sample schemas, Mondial, FIBEN, and the MIMIC demo with GoogleSQL pipelines**. Broader collections make it possible to expand across hundreds of schemas, but their source overlap and individual data terms need to be retained.

Repositories, source files, release cards and documentation were inspected. External databases and suites were **not imported or executed against KumoSQL**. A downloadable artifact, an upstream expected output and a universal equivalence proof establish different things. The recommendations below are proposed additions, not completed integrations.

## Evidence needed for the new sources

Use four separate categories when extracting this material: **equivalent alternatives**, **intentionally different repairs**, **single-query expected results**, and **workloads without correctness labels**. Preserve the original SQL, dialect, schema, constraints, source test and comparison policy. Record separately whether evidence comes from a formal argument, a native regression harness, a fixed database, or an expected rewrite string.

Engine bug witnesses are especially valuable, but they are intended equivalences whose outputs differ on a defective engine. Their classification should carry the affected engine/version and expected fix behavior. Human corrections and perturbations frequently change the intended answer and belong in the negative suite. Transpiled PostgreSQL/DuckDB variants of GoogleSQL are candidates for validation, rather than automatic positive labels.

For every full database, distinguish **fixed complete data**, **schema plus generator**, **schema with external population dependencies**, and **hosted data only**. Code licenses do not automatically cover dataset contents. Sizes and table counts below describe the inspected release or DDL, rather than a proposed reduced fixture.

## New SQL before and after sources

### SQLFluff structural fixes and refusal cases

[SQLFluff's MIT fixture repository](https://github.com/sqlfluff/sqlfluff/blob/main/LICENSE.md) is a particularly close fit because KumoSQL already uses SQLFluff. Its rule files carry `fail_str` inputs, `fix_str` expected output, `pass_str` refusal/no-change cases and dialect/configuration metadata. Here, `fail_str` means a lint violation; it does not mean invalid SQL or a non-equivalence label.

The seven inspected files below contain **119 `fix_str` entries** in total, including **31 ST05 mappings**. That is an exact textual field count for the inspected snapshot, not 119 proven equivalent queries. Partial fixes, configuration branches, unsupported dialects and changes to output contracts still need classification.

A small first engine batch can identify **six Trino cases, two Spark positive pair candidates, one Spark NULL negative, three PostgreSQL witnesses and one SQLite witness**. These 13 selections have distinct evidence categories; they are not 13 universal-equivalence proofs. TPC-H appears here as Trino's setup dependency, rather than a newly discovered database.

JoinEquiv's projection boundary can be tested independently with an authored two-row counterexample. Give NOT NULL tables R and S one row each, use an always-false join condition and project `SELECT DISTINCT 1`: the inner join is empty, while intersecting the projected LEFT/RIGHT joins yields `{1}`. This reasoning shows why a full-row relational identity does not automatically license arbitrary projected SQL. It is our counterexample, not a released paper fixture.

The three R08 cases have more specific guards: 20483's projected non-NULL column/filter separates unmatched sides; 20486 projects both one-column source rows; 20608 uses always-true predicates and full-row projection. Those inspected cases avoid the counterexample above. Prefer the licensed engine regression over copying JoinEquiv's unlicensed generator code; an upstream replay is still fixed-fixture evidence rather than an all-input proof.

## Suggested extraction batches for implementation

1. **Small source-backed regressions:** extract SQLFluff ST05/ST02/ST04, named no-op cases, Trino alternatives and a few engine witnesses. Add Arcwise repairs as negatives. Retain the source case ID and original dialect in every record.
2. **Independent native results:** select Mozilla tests with complete supplied inputs, then GoogleSQL reference tests where the harness/data are available. Use native BigQuery confirmation for features whose production semantics matter.
3. **Complete small databases:** import Oracle HR, Mondial and SmallBank/TATP, then CO/SH and FIBEN. Record all tables, declared constraints, row counts, load/version metadata and schema adaptations.
4. **Full transformation projects:** use the MIMIC demo and compatible concepts, then the bootstrapped orders SQLX demo. Compile Dataform and capture initial/incremental state explicitly; merely stripping SQLX blocks does not exercise the full project.
5. **Scale and diversity:** add LDBC SF0.003, selected new-domain RelBench/CTU/The Join databases and SQLStorm/CEB workloads. Deduplicate their source lineage before reporting coverage growth.

These are proposed implementation batches. None was executed during this research. Universal-equivalence labels still need a proof under stated assumptions; successful native runs establish agreement on the chosen database and comparison policy.
