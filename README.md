# KumoSQL

KumoSQL helps you change BigQuery SQL and Dataform models with evidence instead of hope. It is built around three questions:

1. **What depends on this query, table, or column?** Pipeline analysis traces model and column lineage and shows the blast radius of a change.
2. **Where is the same work being done repeatedly?** Duplicate and near-duplicate SELECT detection finds logic that could be shared.
3. **Can a proposed change be shown to preserve behavior?** Rewrites are small, deterministic transformations, checked by static proof, SMT, synthetic-data comparison, and BigQuery dry runs. Tests decide what is trusted, not an LLM at runtime, and output that cannot be verified is flagged rather than reported as a success.

New here? The [Getting Started guide](docs/getting-started.md) goes from install to a first verified rewrite, a pipeline impact report and the browser UI.

## Local browser UI

Start the local editor with `python -m kumosql.ui` (the form that works on locked-down Windows machines too) and open `http://127.0.0.1:8765/`. It serves only on `127.0.0.1`, keeps pasted SQL local, and shows your own project on the Query graph, Cost and Change reports pages. Scopes, data sources and BigQuery settings live under Settings. Details: [docs/ui.md](docs/ui.md).

## Tags

Tags are KumoSQL's own labels on tables, views, functions, procedures and Dataform models, set by hand or by rule and never written back to BigQuery. See [docs/ui.md](docs/ui.md#tags).

## Rewrite rules

Each transformation is a rule in a registry; a shared driver handles SQLX blocks, `${...}` interpolations, strict parsing, formatting, byte-for-byte no-ops and CTE dependency checks. The rules and what each one does: [docs/rewrite-rules.md](docs/rewrite-rules.md#rewrite-rules).

## Subquery lifting

`kumosql.lift_subqueries()` promotes every `FROM`/`JOIN` subquery into a named top-level CTE, for BigQuery SQL and Dataform SQLX, and leaves scalar, `EXISTS` and correlated subqueries alone. See [docs/rewrite-rules.md](docs/rewrite-rules.md#subquery-lifting).

## Test the authored SQL fixture

The repository includes 32 hand-written sample queries at `tests/fixtures/sql_subquery_samples.json`. Each entry contains only an `id` and `sql_text`. The samples cover nested relations, joins, CTE placement, DML, DDL, and Dataform SQLX. The full fixture test uses:

```shell
pytest -m slow tests/test_workbook_fixture.py
```

Override its path with `KUMOSQL_TEST_FIXTURE` to test another CSV or JSON fixture. The test fails unless every sample has zero remaining relational subqueries and no fatal diagnostics. A separate unit test verifies the small fixture shape.

The normal unit suite (it skips the `slow` marker and needs `pip install -e ".[dev]"`; the full run takes a few minutes) is:

```shell
python -m pytest
```

Use `python -m pytest` rather than bare `pytest` so the repository root is importable. CI (`.github/workflows/tests.yml`) runs `python -m pytest -m "not slow"` on the floor and the current `sqlglot` release.

## Equivalence provers

Every rewrite is checked before it is trusted. The structural prover (`kumosql.prove_equivalent`), synthetic-data comparison in DuckDB (`check_result_equivalence`), the Z3 prover (`prove_equivalent_smt`) and the algebraic prover with an optional SQLSolver stage (`kumosql.sqlsolver_backend.prove_equivalent`) are described in [docs/provers.md](docs/provers.md). False negatives are acceptable; false positives are not.

## Output properties

`kumosql.output_properties.infer_properties(sql, constraints, schema)` states, without running the query, which output columns are never NULL, which sets of columns are unique and how many rows it returns at most (so whether a scalar subquery can return several rows). It works from declared NOT NULL columns and keys, understands `GROUP BY`, `DISTINCT`, joins (a join can destroy uniqueness, an outer join makes the other side nullable again), `COUNT` versus `SUM` over an empty input and filters that establish non-NULL values, and names the declared facts each conclusion rests on. Unknown stays unknown. Details, rules and the evaluation (labelled cases checked on random databases, held-out cases, and SQLSolver's queries) are in [docs/output-properties.md](docs/output-properties.md); `python tools/output_properties_bench.py` reruns it.

## Incremental models versus full refresh

`kumosql.incremental` reads a Dataform incremental model (`when(incremental(), ...)`, `${self()}`, `uniqueKey`, incremental `pre_operations`), replays batches of source inserts, updates and deletes in DuckDB the way Dataform runs it, and checks the table against a full recompute after every batch. `check_incremental(model, sources, kinds)` answers for a *contract* (the kinds of source change allowed): `safe` through a proof rule, `diverges` with a minimised counterexample that replays on its own, or `unknown`. `python -m kumosql incremental-report PROJECT` runs it over every incremental model of a Dataform project. See [docs/incremental.md](docs/incremental.md); the evals are `python tools/incremental_bench.py` (authored cases) and `--track pgivm` (adapted pg_ivm workloads).

## Constraint-dependent rewrites

A rewrite that is only valid under declared NOT NULL columns, keys or foreign keys (dropping a join a foreign key makes redundant, `NOT IN` to `NOT EXISTS`, dropping a `DISTINCT`) is proved from those facts, and `kumosql.constraint_dependence.needed_guarantees` reports a minimal set of them: remove any one and the proof fails. `TableConstraints.foreign_keys` carries foreign keys (filled from BigQuery table constraints). See [docs/constraint-rewrites.md](docs/constraint-rewrites.md); `python tools/constraint_rewrite_bench.py` reruns the eval.

## Whole-pipeline analysis

`load_sqlx_project(root)` loads a Dataform project (or a folder of `.sql` files) into a `Pipeline` with model and column lineage, impact, duplicates and a release gate (`python -m kumosql pipeline-report`). Table profiles, finding tables that already provide the same thing or hold it at a finer grain, and comparing outputs before and after a refactor are in [docs/pipeline-analysis.md](docs/pipeline-analysis.md).

## Cost, change reports and the BigQuery dry run

`dry_run` and `check_rewrite` ask BigQuery to plan a query without running it; cost attribution from job history, change reports and refactoring proposals build on the pipeline graph. See [docs/cost-and-change-reports.md](docs/cost-and-change-reports.md).

## Join ordering and cardinality estimation

`kumosql.joinorder` estimates the sizes of sub-joins from statistics gathered once from the data, and picks bushy join orders with DPccp. Both run in pure Python with no database. On STATS-CEB its sub-plan Q-error is 17 at p99, against 3,482 for Postgres 16 and 156 to 1,027 for the published learned estimators. Its plans run the workload in 98.8 s in DuckDB, against 275 s for DuckDB's own optimizer. `python tools/joinorder_bench.py stats-ceb --repo PATH` reruns it. See [docs/joinorder.md](docs/joinorder.md) for the method, the benchmarks and credits.

## BigQuery and Dataform syntax coverage

`tests/fixtures/bq_syntax/` holds about 320 small, valid cases (one per GoogleSQL or Dataform construct) and a manifest. Every case runs through parsing, the Dataform loader, graph and lineage, fingerprint SQL, cleanup and rewrite, formatting and the SMT prover; gaps are recorded in `known_gaps.json` so a new one fails the suite. [docs/bigquery-syntax-coverage.md](docs/bigquery-syntax-coverage.md) has the per-family table, the list of gaps and who owns each, and how to dry-run the fixtures against BigQuery (free, never billed) with `python tools/bq_dry_run_manifest.py --project PROJECT`.

## Analytical SQL coverage (TPC-DS, DSB, SQLStorm)

`tools/analytical_coverage.py` runs public analytical benchmark queries through every stage above, and executes each rewrite against its original in DuckDB on generated tables. The corpora are [SQLStorm](https://github.com/SQL-Storm/SQLStorm) (MIT; Schmidt et al., VLDB 2025: LLM-generated StackOverflow, TPC-H, TPC-DS and JOB queries, plus the official TPC-H, TPC-DS and JOB templates) and [DSB](https://github.com/microsoft/dsb) (MIT; Ding et al., VLDB 2021). `tools/benchmark_corpora.py` fetches them at pinned commits outside git, generates the DSB queries with DSB's own `dsqgen`, and holds one query in five out for final scoring. [docs/analytical-sql-coverage.md](docs/analytical-sql-coverage.md) defines the score, lists the results and covers the bugs this found: the formatter re-cased table and column names, windows and `ORDER BY ... LIMIT` were never provable, lineage through `SELECT *` CTEs reported `*`, and generated data ignored query constants.

```
python tools/benchmark_corpora.py fetch sqlstorm dsb
python tools/analytical_coverage.py --limit 200 --reasons
```

## CLI

Every command prints `--help`.

**Locked-down machines.** pip installs each command as a launcher (`kumosql-ui.exe` on Windows). If your organisation blocks `.exe` files, or the Scripts folder is not on `PATH`, use Python itself: `python -m kumosql COMMAND ARGS...` runs any command in the table, with or without its `kumosql-` prefix, so `python -m kumosql ui --port 8766` is `kumosql-ui --port 8766`, `python -m kumosql rewrite-sql in.sql` is `rewrite-sql in.sql`, and `python -m kumosql pipeline-report ROOT` is `kumosql-pipeline-report ROOT`. `python -m kumosql` alone lists the commands. The UI and the report tools also run as modules directly: `python -m kumosql.ui`, `python -m kumosql.change_report`, `python -m kumosql.ci_check`. Commands in this document are written in the `python -m` form, which works everywhere; the launcher names (`kumosql-ui`, `rewrite-sql`, ...) are optional shortcuts for the same programs.

| Command | Purpose |
| --- | --- |
| `python -m kumosql.ui` | Local browser UI (`--project DIR`, `--git URL`, `--branch`, `--refresh`, `--jobs FILE`, `--port`, `--no-browser`) |
| `python -m kumosql rewrite-sql` | Apply rules with verification, optional idempotence, planner and synthetic checks |
| `python -m kumosql lift-subqueries` | Lift `FROM`/`JOIN` subqueries into CTEs (`--report` prints a summary) |
| `python -m kumosql prove-sql-equivalent` | Structural equivalence proof for two queries |
| `python -m kumosql prove-sql-smt` | Z3 equivalence proof for two queries |
| `python -m kumosql prove-sql-sqlsolver` | Algebraic proof, then optional SQLSolver (`--backend`, `--check` tests the setup) |
| `python -m kumosql prove-tables LEFT RIGHT --project DIR` | Prove two models of a Dataform project equivalent, layer by layer, using saved equivalences |
| `python -m kumosql equivalence list\|add\|remove` | Saved "column X of table A is column Y of table B" declarations |
| `python -m kumosql pipeline-report` | Whole-pipeline lineage, impact, duplicates, coverage and release gate |
| `python -m kumosql scopes` | Manage saved scopes (`list`, `add`, `remove`, `fields`, `refresh`) |
| `python -m kumosql compare-outputs` | Generate SQL that compares pipeline outputs before and after a refactor |

| `python -m kumosql ci-check` | Turn a change report into a check conclusion and comment |

## Smoke test on a work-laptop replica

Every fix to loading, git, the graph or logging is tested end to end against a realistic repository before it is called done. `python tools/make_dataform_fixture.py DIR [--models 3000] [--config yaml|json|both]` writes a synthetic Dataform project shaped like a large enterprise one: thousands of `.sqlx` files, paths over 260 characters, `workflow_settings.yaml` and/or `dataform.json`, `includes/`, declarations, assertions, operations, incremental tables, `tags: []` and missing config fields, `js` blocks, pre and post operations, near-duplicates, broken refs, and files with a byte-order mark, CRLF, a non-UTF-8 encoding, or a config and no query. `python -m kumosql smoke --repo URL` then starts the real server in a scratch folder (and, once everything else passed, restarts it on the same data folder and fails unless the saved project shows up within `--second-start-limit` seconds, default 20; `--no-second-start` skips this), blocks SSH, picks a local data folder outside AppData, connects the repository through the API, waits for the graph and the analysis, opens every page and every Settings section in a real browser, and fails on any console error, failed or erroring request, server that stops answering for more than 10 seconds, or `ERROR` line in `ui.log`, any "Ambiguous mapping" gap, and any graph node in `--forbid-dataset` (default `fx_scratch`, the fixture's default dataset, where wrongly resolved refs land). It writes `smoke-report.json` and screenshots to its work folder and exits non-zero on failure. The browser is driven with Playwright (`python -m pip install --user playwright`); it uses Microsoft Edge or Chrome when installed, so no browser download or administrator rights are needed (`--browser`, `--browser-path`). Use an https URL for the repository to exercise the work-laptop path, or `--allow-ssh` to leave SSH alone.
